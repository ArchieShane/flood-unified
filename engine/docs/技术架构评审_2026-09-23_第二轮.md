# 技术架构评审 · 第二轮（2026-09-23）

上一轮（`技术架构评审_2026-09-23.md`）评的是**结构**：怎么分层、怎么缓存、怎么不把服务卡死。近期七条与中期四条都已落实，那些结论仍然成立。

这一轮换个角度，评的是**正确性**：系统给出的数，有多少是可信的。结论比上一轮难看。

---

## 0. 结论

**结构是好的，数有问题。**

分层、缓存、任务池、本体这套骨架经得起看，上一轮的改造确实见效了：启动 2.5 s、重接口不再阻塞轻接口、35 个动作声明与实现一一对应、`Cache` 的落盘路径（临时文件 + `os.replace`、坏 pickle 自愈、磁盘故障整体降级）写得干净。

但这一轮在**算数的那一层**找到了七处会静默给出错误数字的缺陷，其中三处直接影响演示时摆在屏幕上的头条数：

- **预算约束是坏的**。给 70 万 AED 的预算（不限预算时只花 25 万），方案反而被砍掉 51 行派单、少花 7 万。实测，见 §2.1。
- **「省下多少分钟」在泵最有价值的场景下恒为 None**，下游把它当 0 处理，于是报告里会出现「那台泵并没有改变退干时刻」——正好说反。
- **达标率有两套口径**，差 270 分钟，同一页上的两个数互相矛盾。

另有一类更隐蔽的问题：**生命周期的阶段链只进不退**，现场二次积水后系统仍判「已退干」，并允许把一个正在 0.6 m 积水的点关掉。这在演示里不会出现（没有真实记录），一旦接入客户真实数据就会出现。

**建议**：§2 的七条在给客户看任何调度费用数字之前必须修；§3 的六条在接客户真实记录之前必须修；§4、§5 可以按计划排。

## 1. 现在这套系统长什么样

| 项 | 数 |
|---|---|
| Python | 16,565 行 / 63 个模块 |
| 前端 | 1,397 行（`app.js` 1,079 + `i18n.js` 139 + `index.html` 179） |
| 测试 | 37 个文件 / 147 个用例（144 过、3 跳过），**行覆盖 55.2%** |
| 配置 | 24 段 / 616 个叶子键（`[dispatch]` 一段就 173 个） |
| HTTP 接口 | 31 条路由 |
| 本体 | 14 对象 / 22 关系 / 23 规则 / 35 动作 |
| 内部依赖 | 174 条边，3 处循环 |

**耦合形状**：`state.py`（782 行）import 了 63 个模块里的 32 个，所有路由都经过它。它同时干三件事——装载并持有数据、决定缓存策略、实现 30 个业务用例。这是整个系统的单点：任何一个下游模块改接口，都要回来改它。

**三处循环依赖**，都靠函数内延迟 import 打断：

```
feeds ↔ lifecycle
dispatch ↔ dispatch2          ← 这一处是真问题
ontology.agent → serve → state → ontology.agent
```

`dispatch` 和 `dispatch2` 合计 1,601 行，互相调用。它们不是按职责分的，是按版本分的（v1/v2），`[dispatch].solver` 选哪个。v1 的代码路径现在不走，但还活着，而且里面有 §2.5 那条缺陷。

**命名陷阱**：配置里同时有 `[standard]`（服务标准：目标重现期、可接受水深、年度预算）和 `[standards]`（水力与几何参数：入流时间、缓冲距离、道路分级）。两者都是热路径，差一个字母，写错了要么 KeyError 要么静默取到另一套参数。

## 2. 会给出错数字的（修之前别给客户看费用）

### 2.1 预算约束把「优先级 × 小时」当成钱算进去了 ✅实测

`swbrain/dispatch2.py:292`

预算行想从目标函数系数 `cvec[i]` 还原出纯行程费用，只减掉了 tie-break 项 `1e-3·V·tv`，却漏掉了到达惩罚项 `arrival_hours_weight · wp · (tv+avail)/60 / den`（`dispatch2.py:253`）。乘回 `V` 之后，每个派单变量往预算里塞进 `wp·(tv+avail)/60·V` 的幻影 AED。

用真实数据实测（10 年 + 20% CC，决策时刻 210 min，平衡目标）：

| 给的预算 | 实际花费 | 用掉 | 派单行数 |
|---|---|---|---|
| 不限 | 252,490 | — | 236 |
| 700,000 | 181,015 | 26% | 185 |
| 400,000 | 197,833 | 49% | 192 |
| 200,000 | 130,014 | 65% | 128 |
| 100,000 | 67,473 | 67% | 73 |

**最干净的判据在第二行**：70 万的预算是不限预算时花费的 2.8 倍，本该完全不起作用，却砍掉了 51 行派单、少花 71,475 AED。客户问「给我 X 预算能做到什么」，系统给的答案系统性偏保守。

现有测试 `tests/test_dispatch2.py:103` 的断言是 `cost <= 3000*1.6 或 plan 为空`，正好放过这个缺陷。

### 2.2 泵最有价值的时候，「省下多少分钟」恒为 None ✅读码确认

`swbrain/replay.py:72`

```python
saved_min = (kb - kp) if (两者都非 None) else (None if kp is None else None)
```

两个分支都是 `None`。也就是「不派泵永远退不干、派了泵能退干」——泵价值最大的那种情况——省下的时间报 None。

下游后果：`replay_plan` 的 `replay_saved_min=None` → `recession.py:238` 按 0 累加 → `recession.py:275` 输出「重演里那台泵并没有改变那些点的退干时刻」。这句话在演示里是反的。

### 2.3 达标率有两套口径，差 270 分钟 ✅读码确认

`swbrain/dispatch.py:453` 判的是 `replay_pump_end_min <= target_drain_min`：左边是**从事件开始起算的绝对时刻**，右边是**从决策时刻起算的时限**。

系统其它所有地方（`dispatch.py:263`、`dispatch2.py:351`、`recession.py:135`）判的都是 `t_decide + target + 60`。

配置里 `decision_time_min = 210`、`target_drain_min.default = 360`，于是别处的判据是 630 分钟，这里是 360 分钟。凡是走 `value_from_plan` 的口径——四个预警等级的预置价值、客户预案 A 与 Parsons 2027 方案的并排对比——达标数都被系统性压低，和同一张调度单行上的 `within_target` 自相矛盾。

### 2.4 平行路段的行程时间被相加而不是取小 ✅实测

`swbrain/travel.py:63`：`coo_matrix(...).tocsr()` 对重复的 `(row, col)` 是**求和**。

实测 `out/state/road_edges.parquet`：414,546 条边里有 **7,216 条（1.74%）** 与另一条边共用同一对端点。这些节点对之间的行程时间被高估约一倍，进而影响 `max_travel_min` 的筛选和目标函数。范围有限但真实。

### 2.5 行程上限判据是恒真式 ✅读码确认

`swbrain/dispatch.py:192`：

```python
feas = np.isfinite(travel_min) & (travel_min + avail <= D["max_travel_min"] + avail)
```

`avail` 两边抵消，泵的可用时刻从没进过可行性判断。v1 的第 2、3 波里 `avail_min` 可达数小时，于是 90 分钟的响应上限形同虚设。只在 `[dispatch].solver = "v1"` 时活着（当前配置是 v2），`dispatch2.py:232` 同样写法但上游已过滤，是死代码。

### 2.6 指定非激活情景看单热点时，「按调度单派泵」那条曲线永远不出来 ✅读码确认

`swbrain/state.py:470` 和 `:649` 查 `pay_cache` 用的是 2 元组 `(key, float(t))`，而写入方（`:212`、`:217`、`:230`、`:556`）一律是 6 元组 `(情景, 时刻, 目标, 预算, 路况 id, 鲁棒)`。必然查不到。

`:470` 有用户可见后果：`plan_rows()` 返回 None → `hotspotdetail.curves(plan_rows=None)` → 返回里 `pump` 和 `pump_kpi` 都是 null。`:649` 有兜底，影响小。

一个单元测试就能抓住。

### 2.7 长汇流时间的管段被静默判「不溢」（评审代理报告，我未独立复现）

`swbrain/networkflood.py:100-105`：峰值溢流取**全部历时**的最大值，溢流体积只在 `d >= tc` 的历时上算。`tc` 超过配置里最大历时 1440 min 时，体积恒为 0、`spilling=False`，但峰值仍计入。于是 `total_m3`、`edges_spilling`、`spilling_len_km` 与 `peak_spill_total_m3s` 两个数对不上。

代理构造 tc=200 min 的算例实测：峰值 8.814 m³/s，体积 0，判不溢。现有测试全部用 `tc_min=10`，没覆盖。

### 2.8 抢占释放的泵被两个点同时记功（评审代理报告，我未独立复现）

`swbrain/dispatch2.py:538` 把多余的泵 `busy_until = t` 放回池子，但 `replay.pumps_from_plan` 只读 `arrive_min` / `rate_m3h`，没有结束时刻，最终重演仍让这台泵在原点抽到视界。同一台泵同时出现在 A 点的重演水量和 B 点的调度单里。单次偏差被 30 分钟限住，点数一多会系统性高估退水量。

## 3. 生命周期与本体（接客户真实记录之前必须修）

### 3.1 阶段链只进不退：能关闭一个正在积水的点 ✅逻辑确认

`swbrain/lifecycle.py:338`：`derive_status` 取 `max(stages, key=STAGES.index)`，**与时间戳无关**。任何一次 dry 观测都永久写进 stages。

代理端到端实测：10:00 记一条「已退干」，18:00 记一条「正在积水、0.6 m」→ 状态仍是「已退干」，`ready_to_close` 触发，`close_point` 返回 ok=True。

根因是没有「本次处置周期」的概念。一场雨里退了又涨，是阿布扎比暴雨的常态。

### 3.2 NaN 穿过全部参数校验 ✅实测

`swbrain/ontology/runtime.py:727-730` 的范围检查是 `v < p.lo` / `v > p.hi`，NaN 的比较全为 False：

| 传入 | lo=0 / hi=400 是否放行 |
|---|---|
| `nan` | **放行** |
| `inf` | 拦住 |
| 5.0 | 放行 |
| 900.0 | 拦住 |

12 个 float 参数都一样。`issue_alert(p24_mm="nan")` 返回 ok=True，动作日志里记成一次 `"p24_mm": null` 的成功签发。

更糟的是 `open_event`：先落盘再计算，NaN 写出的那行**不是合法 JSON**，此后每次 `load_events()` 都抛异常，生命周期层整个失效，只能手工删 `out/events.jsonl` 才能恢复。一次失败的动作留下了持久化的毒记录。

### 3.3 `traffic_status` 标 `side_effect=none`，实际出网、计费、写盘 ✅确认

`swbrain/ontology/schema.py:530` 未声明 side_effect（默认 none），但 `refresh=true` 会发 HTTPS 到 Google Routes（按元素计费）、写 `out/traffic_cache.json`、替换全局路况系数。35 个动作里唯一一个标 none 却真出网真写盘的。

演示时对客户说「写动作只有两个」，这条是第三个。

### 3.4 三个 loader 名根本不存在 ✅实测

| 对象类型 | 声明的 loader | Runtime 上有吗 |
|---|---|---|
| Scenario | `load_scenarios` | 没有 |
| Reach | `load_reaches` | 没有 |
| Zone | `load_zones` | 没有 |

这三个对象在 `get()` / `search()` 里内联处理，声明里的名字是错的，而且会经 `to_dict()` 进 `/api/ontology` 和 `docs/本体模型.md`——客户能看到。

**`--check` 的盲区就在这里**：自检查 api 重名、pk 在属性里、derived_by 指向真规则、关系两端存在，但不查 loader 名存不存在、不查 `_act_` 实现在不在、不查 `side_effect` 是否如实。所以自检永远绿。

好消息：35 个动作的 `_act_` / `_sum_` 我逐个核过，一个不缺。

### 3.5 证据优先级：文档写了，代码没实现（评审代理报告）

`swbrain/lifecycle.py:11` 的说明写「客户记录 > 现场观测/993 > 本系统推演」，实际 `build_episodes` 是固定顺序合并，没有任何仲裁；`lifecycle.py:249` 让 `observed_flooded=True` 粘住，后来的 False 改不回来。

代理实测：客户记录说「没积水」+ 同窗口一条 993 说「有」→ 结论 `observed_flooded=True`，而来源标签显示「客户记录」。卡片上写着主来源是客户记录，结论却和客户记录相反，这条还会进 POD/FAR 的分母。

### 3.6 规则可追溯性：23 条里 6 条出处自指 ✅实测

`needs_escalation`、`observation_conflict`、`history_vs_model`、`repeat_offender`、`ready_to_close`、`treatment_effective` 六条的 `source` 写的是「本体规则层」——自己指自己，没有规范或代码出处。演示时点开规则看出处，这六条经不起追问。

另外 `dispatchable` 的说明写「1.5 km 内有排放去处、入流不超过可派排量」，代码里 `r_dispatchable` 只查三个字段，那两个判据藏在上游算好的 `triage` 文本里。`explain_rule` 会把 1.5 km 这个数讲给客户，代码里查不到它。

阈值对得上的我也核了：预警分级的 45/70/90 mm、目标排干时限的 120/180/240/360、接力系数、核验的 POD 0.8 / FAR 0.3——与 `config.toml` 逐个一致。

## 4. 服务与安全（进内网之前必须修）

### 4.1 HEAD 请求完全绕过口令 ✅实测

`swbrain/serve.py` 只覆盖了 `do_GET` 和 `do_POST`，`SimpleHTTPRequestHandler` 自带的 `do_HEAD` 直接走静态文件分支，`_auth` 根本不执行。

实测同一路径：

```
HEAD /data/summary.json   →  HTTP/1.0 200 OK，带 Content-Length
GET  /data/summary.json   →  HTTP/1.0 401 Unauthorized
```

局域网上任一主机不带口令即可枚举 `console/data/` 下每个文件是否存在、多大、什么时候更新——等于免口令知道这台机器装了哪批数据、上一轮批处理什么时候跑的。

### 4.2 畸形请求、404、非 GET/POST 方法一律返回空字节 ✅实测

`swbrain/serve.py:57` 的 `log_message` 假定 `args[0]` 是请求行，但 `send_error()` 传进来的是 `HTTPStatus`，`"/api/" in line` 抛 TypeError，而这一句在**写响应之前**。

实测三种请求都返回 0 字节、连接被直接断开，客户端拿不到任何状态码：

| 请求 | 回应 |
|---|---|
| `GARBAGE\r\n\r\n` | 空字节串 |
| `GET /nosuchfile.txt?key=…` | 空字节串 |
| `DELETE /` | 空字节串 |

也就是说**控制台上任何一个 404 静态资源都得不到 404，而是连接被断**。同一行的 `if "/api/" in line` 还意味着所有非 API 请求（页面、静态文件、401 失败）一条日志都不记——口令爆破和上面的 HEAD 探测都留不下痕迹。

### 4.3 带 `?key=` 的链接会覆盖已登录用户的 cookie ✅实测

`swbrain/serve.py:77` 判定用「cookie 或 query 二选一」，但种 cookie 只看 `"key" in qs`，不看这次是靠谁过的。

实测：带**正确 cookie** + `?key=WRONG-KEY-123` 请求 `/api/health` →

```
HTTP/1.0 200 OK
Set-Cookie: swb_key=WRONG-KEY-123; Path=/; Max-Age=2592000; SameSite=Lax; HttpOnly
```

把 `http://<host>:8766/?key=x` 发给值班员，他点开之后有效 cookie 被换成垃圾，30 天内每次访问都被弹回登录页。暴雨调度时把人锁在系统外。

### 4.4 控制台口令明文写进 `out/dsh_home*/` ✅实测

16 位口令逐字出现在 5 个文件里：

```
out/dsh_home/.agent-presets/drainage/agent.cordis.yml
out/dsh_home/patches/sdk.patch.yml
out/dsh_home/patches/_sdk_composed.yml
out/dsh_home_web/.agent-presets/drainage/agent.cordis.yml
out/dsh_home_web/patches/sdk.patch.yml
```

五个都已 gitignore，**没有进 git**。但 `swbrain/dsh_bridge.py:10` 的模块说明写「密钥只从环境变量读，永不写进仓库」——这句对三个模型 API key 成立，对控制台口令不成立。`out/dsh_home_web/workspace` 还会被 dsh Web UI（3080）索引。

### 4.5 其余（评审代理报告，机制已确认）

- **`feeds.push` 读-改-写没有锁，也不是原子写**（`feeds.py:169`→`:185`）。两个并发的 `POST /api/feed/incidents` 会互相覆盖——暴雨时 993 批量推送正是并发场景。写一半被中断，文件变成半截 JSON，而 `_read_file` 捕获异常后返回空，这个源静默变成「没有数据」而不是报错。
- **POST 正文没有大小上限**（`serve.py:126`）。声明 `Content-Length: 2000000000` 就让服务端一次性申请 2 GB。
- **拉取型外部源不限 scheme、跟随跳转时不剥 Authorization**（`feeds.py:42`）。当前六个源的 url 都是空串，接 ADM 真实接口那天，一个 302 就能把 Bearer token 送到第三方域名。
- **口令可无限次猜，无速率限制，401 还不记日志**。设了口令就自动绑 `0.0.0.0`，全程明文 HTTP，口令按设计跑在 URL 里（会进浏览器历史与代理日志）。
- **登录页用 JS 写 cookie，没有 HttpOnly**（`serve.py:22`），而服务端那条有。走登录表单进来的用户，口令 cookie 页面脚本可读；控制台从 cdnjs 加载 Leaflet。
- **异常消息原样回给调用方**（`serve.py:101`：`str(ex)[:300]`），会带绝对路径、表名。现在有口令挡着。
- **有副作用的 GET**：`/api/traffic?refresh=1`（出网计费）、`/api/gwm_points?run=1`（跑批）。`SameSite=Lax` 在顶层导航 GET 时照样带 cookie。

## 5. 并发与状态（多人同时用才会出来）

服务是 `ThreadingHTTPServer`，一连接一线程。演示时通常只有一个人点，所以下面这些没有暴露过。

1. **切情景是两条独立赋值**（`state.py:206`、`:346`）。A 在切情景、B 的 `/api/dispatch` 插在两条赋值之间 → 拿到新情景的上下文配旧情景的 key，算出的解**落盘**成错的缓存，重启后照样命中。
2. **代码指纹漏了决定结果的模块**（`artifactcache.py:20`）。只哈希固定 28 个顶层名字，漏掉 `tools/hotspot_workbook.py`（热点→管段匹配半径、面积、汇流时间全在这里）、`jobs.py` 的两个 worker、`state.py` 自己。改匹配半径重启，8 个缓存全部照旧命中，积水点数一个不变。反过来 `export.py`、`verification.py` 这些不影响结果的改一行排版就作废整个目录（重算一轮 648 s）。
3. **实测雨型文件不在任何指纹里**。`out/dmt_model/rain_events.json` 一旦生成，事件情景就从「手册梯形」切到「实测雨型水量平衡」，结果量级不同，但缓存不失效。
4. **启动时把自己上一轮的产物当输入**（`state.py:57`）。`glob("*flood_points*.json")` 没排除 `flood_points.system-*.json`，而 `run.py:202` 和指纹计算都专门排除了它。于是重启后 `active_rp` 取决于上次服务最后算的是哪个情景。

### 7.1 转义函数不转单引号，而有地方把它塞进单引号属性 ✅端到端实测

`console/app.js:35` 的 `esc()` 只处理 `& < > "`，不处理 `'`。而 `app.js:346` 和 `:321` 把它的结果放进**单引号**属性：

```js
`<span class="chip" data-reui='${esc(JSON.stringify(u))}'>`
```

阿布扎比的真实片区名带撇号的不少。实测向服务要 `zone_overview`：

```
片区 Al Maqta'          → ui = {"tab":"overview","zone":"Al Maqta'","rp":"50"}
生成的属性在这里断掉    → data-reui='{&quot;tab&quot;: … &quot;Al Maqta'
```

`Hadbat Al Za'faranah`、`Al 'Adlah` 同样。数据里的分布：`schedule.json` 136 处、`proposals.geojson` 48 处、`bottlenecks.geojson` 38 处。

**现在就坏**：问这几个片区，「在地图上显示」那个按钮拿到的是半截 JSON。**同时是注入口**：值里带 `' onmouseover='…` 就能挂事件处理器。

其余转义纪律是好的：52 处 `innerHTML` 赋值对应 352 次 `esc()` 调用，`mdToHtml` 先转义再加标记，链接只认 `http(s)://` 和 `/`。

### 7.2 服务只绑 IPv4，用 `localhost` 访问每个请求多花 0.2–2 秒 ✅实测

服务绑 `0.0.0.0`（IPv4 only），而 `localhost` 在本机先解析到 `::1`：

| 客户端 | `localhost` | `127.0.0.1` |
|---|---|---|
| curl | 0.21 s | 0.003 s |
| Python urllib | 2.04 s | 0.015 s |

演示脚本和给客户的地址用的都是 `localhost`。控制台一个页面十几个请求，光连接就白花两三秒。改一行绑双栈，或者把地址换成 `127.0.0.1`。

### 7.3 结构

`app.js` 1,079 行一个 IIFE，约 20 个模块级可变全局。上一轮评审决定演示后再拆 ES 模块，这个判断仍然成立。

### 收尾核对时又撞上的两条

**启动情景由「盘上哪个预测文件最新」决定**（§5.4 的另一面）。把 `flood_points.system-*` 排除掉之后只是换了个受害者：扫到最新的世界模型文件（情景 50），`ctx_50` 于是被写成世界模型版本，而配置写的是 `flood_source = system`。世界模型「水深只涨不退」，150 个点全判「入流仍大于可派排量」——**50 年一遇的调度单是空的**，演示时点过去就是一片空白。

根子是启动把「碰巧最新的那个文件」建出的上下文写进共享缓存 `ctx_<key>`。改成：启动情景按 `[serve].startup_scenario` 定（留空 = 目录第一个），优先从盘上缓存取；取不到才用预测文件撑一个能起服务的上下文，而且只当自己用，绝不落盘。配置键放 `[serve]` 段，那一段不进指纹，加它不会让热好的缓存作废（放 `[dispatch]` 会，试过）。修完八个情景口径一致，调度单 386–522 行。

**调度缓存随路况快照自失效**（§5 的并发那一类，未修）。路况系列只覆盖某个决策时刻附近的窗口，切到决策时刻差得远的情景（设计情景约 200 min，两场实测雨 765–770 min）就会触发一次刷新；刷新换一个 `traffic["id"]`，内存和盘上的调度缓存全部作废，那一次要等 30–90 s。要根治得把调度缓存的键换成「实际用到的路况系数」而不是全局自增 id，属于 §5.6 那条的设计改动。演示脚本的开场清单里加了一步：把要演的情景各点一遍。
