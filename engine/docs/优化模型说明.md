# 应急调度优化模型说明（第三道防线）

代码在 `swbrain/dispatch2.py`，求解器是 `scipy.optimize.milp`（HiGHS）。本文写的是模型本身：要决定什么、为什么这么建、确切的变量与约束、实测规模、以及这个建法的弱点在哪。所有数字来自 2026-09-24 的真机求解（10 年一遇 + 20% 气候变化，决策时刻 210 min），已含当天对目标函数的两处修正（见 §5 末尾）。

---

## 1. 要决定的是什么

雨峰过去之后，值班的人面对的是一张清单：几百个点在积水，手上有几百台泵、几百辆罐车，分散在 21 个驻地，分属 5 家承包商。要决定的是：

- 哪些点现在派，哪些点等；
- 每个点派几台、派什么型号（12 寸 / 8 寸 / 6 寸三联 / 罐车）；
- 从哪个驻地派，谁先谁后。

判据不是「派得多就好」。派一台 12 寸泵到一个低优先级的点，可能让一条下穿道多淹两小时。所以要的是一个**权衡**：单位时间的积水，值多少钱。

## 2. 为什么不能直接写成「哪台泵去哪个点」

最自然的写法是 `x[u,p] ∈ {0,1}`（第 u 台泵去第 p 个点），目标是最小化总积水时长。这条路走不通，因为**积水时长不是派了几台泵的线性函数**。

一个点的退水过程是：水量 V(t) 按 `dV/dt = 入流 − 自然退水 − 泵排量` 走，泵在到达并架设完之后才开始出力，排量还要按接力级数折减。于是「派 2 台 12 寸」和「派 1 台 12 寸 + 1 台 8 寸」的收益，既不等于两台各自收益之和，也不成比例——入流大于总排量时多派一台是零收益，入流刚好被压住时多派一台是断崖式收益。这是个非线性、非凸的关系，直接写进 MILP 要么线性化到失真，要么变成 MINLP 解不动。

**这套模型的做法是把非线性挪到系数里**：先枚举每个点的若干个「处置包」，每个包用真正的水力重演算一遍，把结果（少了多少积水小时、退干时刻、费用、耗材）变成常数，MILP 只在这些常数上做选择。

## 3. 处置包：模型的基本单位

对每个候选点，`point_packages` 枚举这些包：

| 包的形式 | 枚举范围 |
|---|---|
| 单型号 × n 台 | 每个能在时限内到达的泵型号，n = 1…3 |
| 两型号各 1 台 | 任意两个型号的组合 |
| 罐车 × n 辆 | n ∈ {2, 4, 6}，**仅当该点 1.5 km 内没有可接纳的排放去处** |

两条剪枝：

- **排量不够一半的不枚举**：`n 台 × 折减后排量 < 0.5 × 当前入流` 时跳过这个 n（除非已经是上限 3 台）。理由是入流压不住时加泵基本没收益，留着这些包只会把 MILP 撑大。
- **罐车和泵互斥**：有排放去处的点只枚举泵包，没有的只枚举罐车包。不是模型里的约束，是枚举时就分开了。

每个包都调一次 `replay.replay(过程线, 泵列表, dt=10 min, 视界=t+1440 min)`，拿到：

- `dH` = 加了这个包之后的积水小时数 − 不派泵的积水小时数（≤ 0）
- `delay_min` = 退干时刻比目标排干时限晚了多少（超了才算，不超记 0），以及 `delay_delta_min` = 它减去「不派泵时会晚多少」。**进目标函数的是后者**，理由见 §5
- `cost_aed` = 台班费 + 动员费 + 人工 + 燃油
- `hose_m` / `fuel_l` / `crew_n` = 耗材与班组占用

一个点若 1.5 km 内没有排放去处，就**不枚举泵包**——泵抽上来的水没地方排。这一条与分诊文案、本体规则 `dispatchable`、单点退水三处口径一致（2026-09-23 之前不一致，见 `技术架构评审_2026-09-23_第二轮.md` §8b）。

10cc 第一个窗口里，172 个候选点一共枚举出 **734 个包**。

## 4. 机组类：把几百台泵压成几十个类

逐台建变量没有意义——同一个驻地、同一型号、同一可用时刻的泵是可互换的。`build_classes` 按 `(驻地, 型号, 当前所在点, 可用时刻取 15 min 档, 承包商)` 分组，每组是一个「类」，带一个 `count`（这类有几台）和一整行到所有积水点的行程分钟数。罐车每个驻地一个类。

于是变量从「几百台 × 几百点」降到「几十类 × 几百点」。

## 4b. 行程时间 τ 是怎么来的：地理空间那一层

§5 的目标函数里 `τ[c,p]`（机组类 c 到点 p 的行程分钟）是个常数，但它不是直线距离除以速度，背后有一整层路网分析。代码在 `swbrain/travel.py` 与 `swbrain/dispatch.py` 的 `build_context`。

**做了什么**

| 项 | 做法 |
|---|---|
| 路网 | 41.4 万段有向边（`out/state/road_edges.parquet`），认单行道 |
| 最短路 | `scipy.sparse.csgraph.dijkstra`，边权是通行秒数 |
| 平行路段 | 同一对端点有多条路时取**最小**代价（2026-09-23 之前是相加，见 §11） |
| 积水挡路 | 水深 ≥ 阈值的路段**断开**，低于阈值的代价 **× 3** |
| 重型 / 轻型 | 两套矩阵：重型涉水阈值 0.45 m、轻型 0.30 m。轻型涉不过的水，重型能过 |
| 限重桥 / 净高 | 载重超限或净高不足的桥附近 40 m 内的路段，在**重型**矩阵里断开 |
| 路况 | Google Routes 的时段拥堵系数按驻地套到整行；没有密钥时用阿布扎比时段曲线 × 雨天加成 |
| 首末端接驳 | 起终点到最近路网节点按直线 30 km/h 补上 |
| 四套矩阵 | 驻地→点（重型 / 轻型）、点→点（抢占后转场）、预置驻地→点 |

**积水面从哪来**：积水点自己。每个点按它的积水面积还原成等效圆（`r = √(A/π)`，最小半径 15 m），落在圆内的路段中点就算被淹。也就是说，**要去救的那片积水，本身会挡住去救它的路**——这是自洽的。

> **这一层 2026-09-24 之前从来没生效过。** `pts0["geom"]` 存的是 `Point`（零面积），而判定用的是 `within`——点永远包不住路段中点。实测 374 个积水点全都有几何体，结果断开 0 段、减速 0 段，重型与轻型的行程矩阵逐元素一模一样，而 `travel_method` 一直写着「积水路段加罚/断开」。改成按面积还原等效圆之后：被积水沾到 2,762 段，重型断开 969 段、减速 1,793 段，轻型断开 1,164 段；驻地→点的可达组合从 6,082 降到 5,398，其余里 87.6% 变慢（中位 +1.9 min，最多 +35 min）。

**哪些距离还是直线，不是路网**（都是已知的近似，不是疏忽）

| 用在哪 | 现状 | 为什么 / 影响 |
|---|---|---|
| 点 → 排放口（`discharge_dist_m`） | **直线**（cKDTree 在投影坐标上算） | 决定 1.5 km 的可达判定、接力级数、每台泵要多少软管。软管沿地面走，直线会**低估**，实际接力级数与软管需求都比模型算的高 |
| 罐车运距 | 缺省 5 km、上限 15 km 的**配置值** | 折算成等效排量与周转时间。系统不知道罐车该卸到哪里（卸点位置与接收能力是数据缺口，见 §11） |
| 首末端接驳 | 直线 30 km/h | 只补最近路网节点那一小段，量级通常在 1 min 以内 |
| 积水判定的粒度 | 按**路段中点**是否落在积水面内 | 一条很长的路，中点在积水外但路身穿过积水，抓不到。路网边的中位长度约 60 m，影响有限 |

**算一次要多久**：四套矩阵合计约 12–25 s（374 个点 × 21 个驻地 + 374×374 点对 + 104 个预置驻地），是建一个情景上下文里最重的一步。结果随上下文一起落盘缓存，切情景时不重算。

## 5. MILP 的确切形式

一个滚动窗口一个 MILP。记候选点集 P、点 p 的包集 G_p、机组类集 C、驻地集 D。

**决策变量**

| 变量 | 含义 | 取值 |
|---|---|---|
| `y[p,g]` | 点 p 采用第 g 个处置包 | 0 或 1 |
| `n[c,p]` | 从机组类 c 派几台去点 p | 0 … count_c 的整数 |

`n[c,p]` 只在「类 c 能在该点等级对应的时限内到达」且「该类的型号确实被点 p 的某个包需要」时才建；silo 模式下还要求同一承包商分区。不满足就根本没有这个变量，等于硬约束。

**目标（最小化）**

```
Σ_{p,g} y[p,g] · [ w_p·ΔH[p,g] + α·w_p·Δdelay[p,g]/60 + cost[p,g]/V ]
  +
Σ_{c,p} n[c,p] · [ tcost[c,p]/V + 1e-3·tv[c,p] + β·w_p·extra[c,p]/60 / n̄_p ]
```

- `w_p` 是点的优先级（下穿道、医院、学校这类设施加权，客户重要度加权）
- `ΔH = 派了这个包之后的积水小时 − 不派的积水小时`，**≤ 0**，所以选一个好包会让目标变负
- `Δdelay = 派了之后比目标时限晚多少 − 不派会晚多少`，**≤ 0**
- `V` 是**单位「优先级 × 小时」值多少 AED**。费用除以 V，等于把钱换算成优先级小时，整个目标就统一在一个量纲上
- `α` 延误权重（缺省 1.0），`β` 到达惩罚权重（缺省 1.0）
- `tcost` 是这一台的行程费用（车公里 + 路上人工），跨区还要加一笔市政开工单费
- `1e-3·tv` 是个极小的行程项，用来在等价解之间打破平局，倾向派近的
- `extra = (该类的行程 + 可用时刻) − (该型号最近那一类的行程 + 可用时刻)`，**≥ 0**

**两处基准必须一致，这里踩过坑**（2026-09-24 修）：

整个目标其实是「每个点在『不派』与各个包之间选一个，选谁代价小」。「不派」的代价是 `w·H0 + α·w·delay0/60`，它是个与决策无关的常数，减掉之后就得到上面的增量形式。原来的代码只把 H 减成了增量，`delay` 却留着绝对值——**而「不派」这个选项根本没有 y 变量、一分不罚**。于是对「派了也追不上目标时限」的点，罚会压过收益，模型宁可不派；偏偏这类点是水量大、优先级高的那批。改成同基准之后，平衡目标在 10cc 下从压住 89 个点变成 106 个，加权积水时长降 5.9%。

同样的毛病在到达罚上也有一份：处置包的重演**已经**按该型号最近那一类的行程算过到达时刻了，`n` 变量再按 `w_p × (行程 + 可用时刻)` 罚一遍，等于对最近的那一类也重复收费；而罚额与优先级成正比，结果**优先级越高的点被罚得越狠**。合成夹具里，优先级 300、车程 10 min 的点会输给优先级 60、车程 15 min 的点。改成只罚「比最近那一类多出来的那段」。

**约束**

| # | 约束 | 形式 |
|---|---|---|
| 1 | 每点最多一个包 | `Σ_g y[p,g] ≤ 1` |
| 2 | 型号平衡 | 对每个点 p、每个型号 m：`Σ_{c:型号=m} n[c,p] − Σ_g need[g,m]·y[p,g] = 0` |
| 3 | 类容量 | `Σ_p n[c,p] ≤ count_c` |
| 4 | 驻地班组 | `Σ_{c∈d 的泵类, p} crew_c·n[c,p] ≤ 该驻地可用人数` |
| 5 | 驻地车次 | 重卡 / 轻卡各一行：`Σ n[c,p] / 每车能带几台 ≤ 车数 × 每窗口车次` |
| 6 | 驻地软管 | `Σ n[c,p]·(基础米数 + 接力级数×每级米数) ≤ 该驻地软管` |
| 7 | 燃油（全局一行） | `Σ_{p,g} fuel[p,g]·y[p,g] ≤ 各驻地燃油之和` |
| 8 | 预算（可选） | `Σ_i money_i·x_i ≤ 预算` |

第 2 条是把两组变量绑在一起的关键：**选了包就必须配齐台数，配了台数就必须有包在用**。

第 8 条的 `money_i` 是单独记的一份「这个变量真正花的钱」。这里踩过坑：原来是拿目标函数系数乘回 V 再减掉几项来还原费用，减不干净，把到达惩罚当成钱算进了预算，导致给 1.5 倍于实际花费的预算也会砍掉四分之一的派单（2026-09-23 修）。

**求解**：`milp(c, LinearConstraint(A, lo, hi), integrality=全 1, bounds=(0, ub))`，HiGHS，时限 30 s。全部变量整数，`y` 的上界是 1，`n[c,p]` 的上界是 `count_c`。

> 严格的数学表述（集合、参数、变量、目标、八条约束、重演算子、窗口间的状态转移、两个变体）见**附录 A**。

## 6. 滚动窗口

一次求解不是一个 MILP，是 **8 个**：从决策时刻起，每 60 分钟一个窗口，视界 1440 分钟。

每个窗口开始时重新算一遍可行性（这个时刻各点还剩多少水、入流多大、能不能派泵），只把「还没被服务、水量 ≥ 50 m³、可派泵或可罐车」的点放进候选。窗口之间结转的是状态：

- 派出去的泵占用到它的退干时刻（48 h 内退不干就占到视界）；
- 罐车从驻地池子里扣掉；
- 班组、软管、燃油从驻地余量里扣掉；
- 预算扣掉这一窗口的实际花费；
- **抢占**：某个点入流已被压住（入流 < 30% 现场排量）且剩余水量 30 分钟内能抽完时，多余的泵在下一窗口释放出来（只留排量最小的那台）。

这样做的意义是：不必一次性把所有泵撒出去，先压最要紧的点，退干一个释放一批。

## 7. 三个目标其实只是一个数

「最快退水 / 平衡 / 最省钱」不是三个模型，是同一个模型换一个 `V`：

| 目标 | V（AED / 优先级·小时） | 含义 |
|---|---|---|
| 最快退水 | 1000 | 一个优先级·小时的积水值 1000 AED，钱几乎不重要，能派就派 |
| 平衡 | 100 | 缺省 |
| 最省钱 | 10 | 一个优先级·小时只值 10 AED，除非特别划算否则不派 |

帕累托那三个点就是把这三个 V 各跑一遍完整的滚动求解。

## 8. 鲁棒目标与承包商分区

**鲁棒**（`robust`）：同一个处置包在多个情景的过程线上各重演一遍，`dH`、`delay`、退干时刻按情景权重取期望，再送进同一个 MILP。模型结构一个字没改，只改了系数。

**承包商分区**（`mode = silo / pooled`）：
- `silo` = 各家只能派到自己的分区，跨区的 `n[c,p]` 变量根本不建；
- `pooled` = 可以跨区，每台加一笔市政开工单费（缺省 2000 AED）进 `tcost`。

两种模式各解一遍，给出「集中调度多压住几个点、多花多少钱」。

|---|---|---|

`solve_window` 占 **9.2 s（36%）**，而 HiGHS 本身只有 0.15 s。那 9 秒花在组装约束矩阵，
大头是 pandas 的逐格取值：「73 个类 × 172 个点」的双重循环里每次都 `cand.loc[p, "level"]`、

另外给帕累托三目标 + silo 共用一份处置包缓存。`point_packages` **根本不用 `V`**
（验证过 V=1000 / 100 / 10 枚举出的包完全相同），四遍滚动求解里窗口 1 的 734 个包是重复算的；
命中率 45%，再省 6%。鲁棒目标不走这个缓存（它的包还取决于各情景过程线）。

|---|---|
| 今天之前 | 15.5 s |
| 快路径 + 排量预计算 | 12.6 s |
| 提出逐格 `.loc` | **9.0 s** |
| 再加共用处置包缓存 | **8.5 s** |

两条都在真实数据上验过结果**逐字段一致**（503 行调度单的每一行、三个帕累托点、silo 对比全相同），并各有一条判据钉住。

再 profile 一遍，剩下的已经没有单个大头：重演 4.4 s、枚举包 3.4 s、模拟 3.0 s、组装矩阵 1.9 s、解码 1.8 s、机组分类 1.8 s，比较平——**提速这条线到此收益递减**。

结论很明确：**这个模型的瓶颈从来不是 MILP**（HiGHS 只占 1%）。真正的大头先是重演里的无用功，后是组装矩阵时的逐格 DataFrame 取值——两处都和优化理论无关，纯是工程。换求解器一点用都没有。

## 11. 这个建法的弱点

写清楚比藏着好。2026-09-24 逐条核过，标了各自的状态。

### 已修

**目标函数里两处基准不一致 —— 已修，是今天改动里最要紧的一条。** 详见 §5 末尾。延误罚用绝对值而收益用增量，导致「派了也追不上目标时限」的点被系统性拒派；到达罚对最近的那一类也照收，而罚额与优先级成正比，导致优先级越高的点越吃亏。两处都改成同基准之后，平衡目标在 10cc 下压住点数 89 → 106，加权积水时长降 5.9%。

**抢占释放的泵没反映到最终重演 —— 已修。** 重演现在认 `until_min`，被释放的泵不再在原点被算成抽到视界。**但要说清楚：真实数据上抢占目前一次都没触发**（10cc 平衡与最快退水两个目标下都是 0 行），所以这条修的是潜伏缺陷，当前没有数值影响。抢占的触发条件是「该点还有 >1 台泵在抽、入流已降到现场排量的 30% 以下、剩余水量 30 min 内能抽完」，而窗口 1 之后几乎没有点同时满足这三条。

### 量过之后决定不建

**① 共用同一个排放口的点之间没有耦合。** 各自的重演都假设排放口能接纳，模型看不到它们互相顶托。

量了一下这件事有多大：

| 情景 | 被派泵的点 | 用到的排放口 | 被 2 个以上点共用的口 | 最多几个点共用 |
|---|---|---|---|---|
| 10 年 + 20% CC | 39 | 19 | **0** | — |
| 100 年 | 39 | 34 | 5 | 2 |
| 2024-04 实测 | 57 | 47 | 9 | 3 |
| 2026-03 实测 | 45 | 40 | 4 | 3 |

设计情景下根本没有共用，重情景下也只有个位数的口被 2–3 个点共用。

更要紧的是：**数据里没有排放口的吞吐能力。** `cs` 表里有 `i_cap_p50`（该汇水区各管段承载雨强的中位数）和 `max_ratio`（最大的设计流量/管容比），但它们描述的是汇水区内部的管段，不是这个终点本身能接纳多少。拿 `i_cap_p50 × 面积` 硬凑一个「口能力」，算出来的数和 `max_ratio` 自相矛盾——同一个口，一个说常规雨只用了 13%，另一个算出灌入量是能力的 1923%；另一个口说常规雨已用 2771%，能力却算出 54 万 m³/h。

**拿一个编出来的能力去加硬约束，比不加更坏**：模型会基于一个假数拒绝派泵，而且拒得无声无息。这条改成向客户要数：**出水口 / 泵站的设计过流能力（m³/s 或 m³/h）**，拿到之后这条约束是一行的事（按排放口分组，限制灌入排量之和）。

**⑦ 点到排放口的距离是直线，不是路网。** `discharge_dist_m` 用 cKDTree 在投影坐标上算，而软管要沿地面走。这个距离决定三件事：1.5 km 的可达判定、接力级数、每台泵要多少软管（`50 + 级数 × 100` m）。直线低估的后果是**接力级数与软管需求都比实际低**，而软管在 MILP 里是一条硬约束（§A.4 第 6 条），10cc 下全网只有 115,750 m、中位驻地 1,500 m——低估这件事会让模型以为能派的泵比实际多。要改得算「点 → 排放口」的路网距离（374 × 5,057 对，可只对 1.5 km 内的候选算），或者先加一个可配的绕行系数。还没做。

**⑧ 积水挡路按路段中点判。** 一条很长的路，中点在积水外但路身穿过积水，抓不到。路网边的中位长度约 60 m，所以影响有限；要更准就得拿边的几何去和积水面求交，而现在路网缓存里只存了中点。

**⑥ 罐车没有排队与卸点容量约束。** 同一个数据缺口：罐车拉走的水要卸到某个接收点，而系统不知道接收点在哪、一小时能接多少。现在的建模是「每辆每趟 17 m³、周转时间 = 装 + 运 + 卸 + 返」折算成一个等效排量，只受罐车池总量与每点 6 辆的上限约束。10cc 下平衡目标一次派出 378 辆覆盖 70 个点，现场能不能组织起这么多车次、卸到哪里，模型不知道。同样要向客户要：**罐车的卸水点位置与接收能力**。

### 还欠着

**② 滚动窗口的后几个窗口基本不产出。** 修完目标函数之后，窗口 1 压住 105 个点，窗口 2 压住 1 个，窗口 3–8 全是 0；其中窗口 5–8 连变量都建不出来（泵全忙、罐车用尽），直接短路。真正白跑的是窗口 2–4：要重新算可行性、枚举一两百个包、建矩阵、求解，产出一个点。

不能简单地「连续两窗没产出就停」——「入流仍大于可派排量」那 61 个点正是要等雨峰过去才变得可派的，早停会把它们丢掉。可行的做法是先做一次廉价的上界估计（用最大可用排量算一个 dH 的乐观值），上界都为正就跳过这个窗口的包枚举。还没做。

**④ 费用有两套口径。** 这里说的费用是 v2 口径（台时 + 动员 + 人工 + 燃油 + 车公里 + 罐车台时 + 跨区工单），也是求解器真正在优化的那个。接口顶层还有一个 v1 口径（只有台时 + 动员），同一个方案小三成。两边的说明字段现在互相指认，口径没合并——v1 那套还被客户预案 A 与 Parsons 方案的并排对比用着。

**⑤ 几个参数是假设不是实测。** `V` 的三档取值（1000 / 100 / 10）、延误权重 α、到达罚权重 β、每车能带几台、每窗口几趟车，都没有客户的合同费率或调度规程作依据。

**α 今天变了性质，要重新定。** 修基准之前，延误项是个罚（绝对延误 ≥ 0），起刹车作用；修完之后它是个收益（Δdelay ≤ 0），起油门作用。同样是 α=1.0，模型的激进程度变了——平衡目标的费用从 102 万涨到 167 万。这个数学上是对的（它本来就该这样），但 α 该取多少要跟客户对：**一小时的「比目标时限晚」，相对一小时的「积水」，值几倍？** 现在的 1.0 是「一样重」，纯属占位。

**⑥ 罐车建模粗**（见上，数据缺口）。

## A.3 决策变量

```
y[p,g] ∈ {0, 1}                     点 p 采用处置包 g
n[c,p] ∈ {0, 1, …, q_c}             从机组类 c 派几台去点 p，(c,p) ∈ 𝒩
```

`n` 只在**可行对**上建。记

```
𝒩 = { (c,p) : τ[c,p] 有限
              ∧ τ[c,p] ≤ L[p]
              ∧ ∃ g ∈ 𝒢ₚ 使 ν[p,g,θ_c] > 0
              ∧ ( pooled ∨ 承包商分区(c) ∋ p ) }
```

不在 `𝒩` 里的组合根本没有变量——等价于一条硬约束，但不占约束行。

## A.4 单个窗口的 MILP

**目标（最小化）**

```
min  Σ      Σ     [ wₚ·ΔH[p,g] + α·wₚ·Δδ[p,g]/60 + κ[p,g]/V ] · y[p,g]
    p∈𝒫  g∈𝒢ₚ

   +  Σ        [ γ[c,p]/V + ε·τ[c,p] + β·wₚ·e[c,p] / (60·n̄ₚ) ] · n[c,p]
   (c,p)∈𝒩
```

其中

```
e[c,p] = max( 0 , (τ[c,p] + a_c) − τ*[p, θ_c] )        比该型号最近那一类多出来的到达时间

τ*[p,m] = min      ( τ[c,p] + a_c )                     该型号最近那一类
          c: θ_c=m, (c,p)∈𝒩

n̄ₚ = max( 1 , ( Σ  u[p,g] ) / |𝒢ₚ| )                    点 p 的包平均几台
                g∈𝒢ₚ
```

**约束**

```
(1)  Σ      y[p,g]  ≤  1                                    ∀ p ∈ 𝒫
    g∈𝒢ₚ                                                    每点最多一个包

(2)  Σ            n[c,p]  −  Σ     ν[p,g,m]·y[p,g]  =  0    ∀ p ∈ 𝒫, ∀ m ∈ ℳₚ
   c: θ_c=m                  g∈𝒢ₚ                            型号平衡

(3)  Σ    n[c,p]  ≤  q_c                                    ∀ c ∈ 𝒞
    p∈𝒫                                                      类容量

(4)  Σ           Σ    r_c · n[c,p]  ≤  K_d                  ∀ d ∈ 𝒟
   c∈𝒞ᵖᵘᵐᵖ_d   p∈𝒫                                          驻地班组人数

(5)  Σ                  Σ    n[c,p] / λ[θ_c]  ≤  Y[d,v]·T   ∀ d ∈ 𝒟, ∀ v
   c∈𝒞ᵖᵘᵐᵖ_d: 车类=v   p∈𝒫                                    驻地车次

(6)  Σ           Σ    (h₀ + σₚ·h₁) · n[c,p]  ≤  H_d         ∀ d ∈ 𝒟
   c∈𝒞ᵖᵘᵐᵖ_d   p∈𝒫                                          驻地软管

(7)  Σ     Σ     φ[p,g] · y[p,g]  ≤  F                      全网燃油（一行）
    p∈𝒫  g∈𝒢ₚ

(8)  Σ     Σ     κ[p,g]·y[p,g]  +  Σ        γ[c,p]·n[c,p]  ≤  B      预算（可选）
    p∈𝒫  g∈𝒢ₚ                     (c,p)∈𝒩
```

**说明三处**

- **(2) 是把两组变量绑在一起的那条**。选了包就必须配齐台数，配了台数就必须有包在用。没有它，`y` 和 `n` 会各走各的。
- **(8) 用的是真实花费 `κ` 与 `γ`，不是目标函数系数**。曾经的写法是拿 `cvec·V` 再减掉几项来还原费用，减不干净，把到达罚当成钱算进了预算——给 1.5 倍于实际花费的预算也会砍掉四分之一的派单。现在单独记一份 `money` 向量。
- **(4)(5)(6) 只对泵类成立**。罐车不占班组与软管，它的约束是 (3) 的类容量（每个驻地的罐车数）与包枚举时的每点上限 6 辆。

**求解**：`scipy.optimize.milp`（HiGHS），全部变量整数，时限 30 s。

## A.5 处置包的参数从哪来：重演算子

这是整个建模的关键一步——**把非线性挪到常数里**。

点 p 的积水过程由一维水量平衡刻画。记 `V(t)` 为 t 时刻的积水体积，`e(t)` 为入流，`ñ(t)` 为自然退水能力，泵集 `𝐏` 中每台泵 j 有到达时刻 `A_j`、排量 `R_j`、释放时刻 `U_j`（没有就是 +∞）：

```
现场泵能力     cap(t) = Σ   R_j · 1{ A_j ≤ t < U_j }
                        j∈𝐏

这一步能拿走的   avail(t) = V(t)/Δt + e(t)
自然退走       tn(t)    = min( ñ(t) , avail(t) )
泵抽走         tp(t)    = min( cap(t) , max( avail(t) − tn(t) , 0 ) )

水量递推       V(t+Δt)  = max( V(t) + ( e(t) − tn(t) − tp(t) )·Δt , 0 )
```

记这个递推的解算子为 `ℛ(𝐡ₚ, 𝐏)`（`𝐡ₚ` 是该点的过程线），并定义两个泛函：

```
积水小时        H(V) = Δt · | { t : V(t) > V_min } |
退干时刻        E(V) = min { t : V(t) ≤ V_min }      没有就记 +∞
迟到多少        δ(V) = max( 0 , ( min(E(V), 视界) − t_now ) − 目标排干时限ₚ )
```

于是包 g 的两个系数是

```
ΔH[p,g] = H( ℛ(𝐡ₚ, 𝐏_{p,g}) ) − H( ℛ(𝐡ₚ, ∅) )        ≤ 0
Δδ[p,g] = δ( ℛ(𝐡ₚ, 𝐏_{p,g}) ) − δ( ℛ(𝐡ₚ, ∅) )        ≤ 0
```

**两项必须同减去「不派」的那个值。** 这不是风格问题，是正确性问题：真正的目标是「每个点在『不派』与各个包之间选代价最小的那个」，写出来是

```
min  Σ   [ 不派 ] 或 [ 某个包 ]
    p∈𝒫

其中  代价(不派)   = wₚ·H₀ₚ + α·wₚ·δ₀ₚ/60
      代价(包 g)   = wₚ·H_{p,g} + α·wₚ·δ_{p,g}/60 + κ[p,g]/V
```

`Σₚ 代价(不派)` 是与决策无关的常数，减掉它就得到 A.4 里的增量形式。**只减一半就错了**——2026-09-24 之前 `H` 减了、`δ` 没减，而「不派」这个选项根本没有 `y` 变量、一分不罚，于是「派了也追不上目标时限」的点被系统性拒派。修完之后 10 年一遇 + 20% 气候变化下压住点数 89 → 106。

`ℛ` 是非线性非凸的（`min` 与 `max` 的嵌套、`1{·}` 的跳变），直接写进 MILP 要么线性化到失真，要么变成解不动的 MINLP。预先枚举包、逐个重演成常数，是这套建模的全部技巧。代价是点与点之间不再耦合（见 §11 ①）。

## A.6 滚动：窗口之间的状态转移

记窗口 k 的时刻 `t_k = t₀ + (k−1)·Δw`（`Δw` = 60 min，`k = 1…8`，视界 `t₀ + 1440 min`）。窗口 k 的 MILP 记作 `𝖯(t_k; S_{k−1}, 𝐪_{k−1}, K_{k−1}, H_{k−1}, F_{k−1}, B_{k−1})`，解出 `y*, n*` 之后：

```
已服务集合    S_k    = S_{k−1} ∪ { fp(p) : Σ_g y*[p,g] = 1 }

候选集合      𝒫_{k+1} = { p : fp(p) ∉ S_k
                            ∧ V_p(t_{k+1}) ≥ 50 m³
                            ∧ ( 可派泵(p) ∨ ( 有罐车 ∧ ¬有排放去处(p) ∧ 入流可压住(p) ) ) }

机组占用      busy_u ← done_u                （派出去的泵占用到它的退干时刻，
                                               48 h 内退不干就占到视界）
类容量        𝐪_k   ← 由 { u : busy_u ≤ t_{k+1} } 重新分类
班组          K_d   ← K_d − Σ_{c∈𝒞ᵖᵘᵐᵖ_d, p} r_c·n*[c,p]
软管          H_d   ← H_d − Σ_{c∈𝒞ᵖᵘᵐᵖ_d, p} (h₀ + σₚ·h₁)·n*[c,p]
燃油          F_d   ← F_d − Σ_{p,g} φ[p,g]·y*[p,g] · F_d/F      （按各驻地余量摊）
预算          B     ← max( 0 , B − 本窗口实际花费 )
罐车          每个驻地的罐车池扣掉本窗口用掉的
```

**抢占**：若点 p 在 `t_{k+1}` 时仍有 >1 台泵在抽，且

```
e_p(t_{k+1}) < 0.3 · cap_p        （入流已降到现场排量的 30% 以下）
V_p(t_{k+1}) / ( cap_p − e_p(t_{k+1}) ) · 60 ≤ 30 min      （剩余水量 30 min 内能抽完）
```

则除排量最小的那台外，其余泵置 `busy = t_{k+1}` 放回池子，并在调度单行上记 `U_j = t_{k+1}`（`ℛ` 的释放时刻，见 §A.5）。

> 实测：真实数据上这个条件目前一次都没满足过（10cc 的平衡与最快退水两个目标下都是 0 行）。

## A.7 两个变体

**鲁棒目标**。给定情景集 `𝒮` 与权重 `π_s`（`Σ π_s = 1`），把包的两个系数换成期望：

```
ΔH[p,g] ← Σ   π_s · [ H( ℛ(𝐡ₚˢ, 𝐏_{p,g}) ) − H( ℛ(𝐡ₚˢ, ∅) ) ]
          s∈𝒮

Δδ[p,g] ← Σ   π_s · [ δ( ℛ(𝐡ₚˢ, 𝐏_{p,g}) ) − δ( ℛ(𝐡ₚˢ, ∅) ) ]
          s∈𝒮
```

**每个情景减自己的基线**。某情景下该点不积水时，该项记 0。MILP 的结构一个字没改。

**承包商分区**。`silo` 模式下 `𝒩` 只保留同分区的组合；`pooled` 模式下允许跨区，但跨区的 `γ[c,p]` 加一笔市政开工单费（缺省 2000 AED）。两种模式各解一遍，给出「集中调度多压住几个点、多花多少钱」。
