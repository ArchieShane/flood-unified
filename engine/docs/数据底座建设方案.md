# 「会思考的排水系统」数据底座建设方案

**面向对象**：阿布扎比市政与交通局（DMT）及阿布扎比市市政局（ADM）雨水排水管理方
**编制方式**：以终为始。先写清系统要做哪些决策，再倒推每个决策需要什么数据产品，再落到数据源、感知、平台、治理与分期。不受现有数据限制，但每一项都标明现状，让差距一眼可见。
**版本**：V1.0，2026-09-16

---

## 1. 一句话定义

数据底座不是「把所有数据收进来」，而是**让五类排水决策每一次都能被算出来、被检验、被追溯**的最小数据集合，加上让它持续更新的采集与治理机制。

判断一个数据底座建得对不对，只看一件事：系统输出的每一条建议，能不能回答「依据哪几条数据、这些数据多准、什么时候采的、错了怎么发现」。

---

## 2. 以终为始：系统要做的五类决策

「会思考的排水系统」最终输出的是**在什么时间、什么位置、增加或调整哪个设施**，以及实施后**还剩多少风险、怎么对账**。拆开是五类决策，每类对数据的要求不同。

| 决策 | 要回答的问题 | 对数据的核心要求 |
|---|---|---|
| D1 状态研判 | 哪段管、哪个片区、哪个出水口最先出问题，在多大的雨下出问题 | 管网几何与标高完整、流向可信、汇水面积可算、设计雨强有依据 |
| D2 时机 | 立即做、雨季前做、事件前做，还是进年度资本计划或并入在批项目 | 预报、潮位、维护窗口、审批周期、预算年度 |
| D3 设施选择与效果 | 扩管、调蓄、加泵改闸、连通、拓扑修正，各能改善多少、花多少钱 | 可运行的水动力模型、有观测校准、成本费率、土地可用性 |
| D4 剩余风险 | 方案实施后哪里仍会积水、影响谁 | 模型结果栅格、建筑与人口暴露、关键设施位置 |
| D5 验证与对账 | 每场雨之后预测对不对、方案有没有起作用 | 事件级观测：雨量、水位、积水点、泵站运行、影像 |

前三类决定「方案好不好」，后两类决定「方案能不能被相信」。现有系统在 D1、D2 上已经跑通，D3 一半，D4、D5 完全没有数据支撑。这就是数据底座要补的方向。

## 4. 分层架构

```
L5 决策与反馈层（控）   建议库 · 干预集合 · 方案与排期 · 承诺与就绪度 · 对账记录 · 人工确认与实施回写
L4 模型与状态层（监）   排水图 · 承载雨强等状态量 · 水动力模型与世界模型 · 情景库 · 模型结果仓 · 校准记录
L3 观测层（测）         雨量 · 潮位 · 液位流量 · 泵闸 SCADA · 积水点（投诉/巡检/摄像头/影像）· 预报
L2 地形与环境层         DEM/DSM · 不透水率 · 用地 · 土壤渗透 · 海岸线 · 暴露对象
L1 资产台账层           管 · 节点 · 出水口 · 泵闸 · 蓄渗设施 · 竣工与检修历史 · 质量标签
L0 基准与编码层         统一时空基准 · 资产编码 · 事件编号 · 版本与时间语义
横切                    数据质量与血缘 · 接口契约 · 元数据目录 · 权限与安全 · 审计
```

### 4.1 L0 基准与编码层：先把「同一个东西」说清楚

- **水平基准**：WGS84 / UTM 40N（EPSG 32640），与阿布扎比大地参考系统的转换参数固化在底座里。现有三个库里 4326、32640、32639 并存，跨库空间相交时不转换会静默返回零行，这是第一个要治的病。
- **垂直基准**：管底标高、井盖标高、DEM、潮位必须换到同一基准。现有台账是 MSL 加 100 的本地基准，潮位站用的是海图基准，DEM 用的是大地高。底座提供一张换算表和一个换算函数，所有入库数据落地时统一。
- **资产编码**：沿用 ADM 的 unitid 编码规则（如 SW_区_片_类型_序号），要求每个物理设施只有一个编码，编码在竣工图、GIS、SCADA、维修工单四处一致。现状：GIS 与 SCADA 之间没有对应关系，是接遥测的第一道坎。
- **事件编号**：一场雨一个编号，串起预报、观测、预测、对账、方案效果评估。
- **时间语义**：每条记录带「数据代表的时间」与「入库时间」两个字段；每次计算带 run_id 与所依据的网络版本。没有这两条，事后无法回答「当时为什么这么判」。

### 4.2 L1 资产台账层：把质量标签当成正式字段

每张资产表在业务字段之外，增加一组**质量标签字段**，由入库规则自动填写，进入所有下游计算的置信度：

| 标签 | 含义 | 例 |
|---|---|---|
| 标高有效性 | 上下游标高是否存在、是否顺坡、坡度是否在合理区间 | ok / 逆坡 / 过平 / 无标高 |
| 流向来源 | 流向来自资产字段、由标高推断、由拓扑推断、还是猜的 | asset / invert / hops / guess |
| 终点类型 | 这一支最终到哪里 | 出水口 / 泵站 / 渗井 / 封堵端 / 断头 |
| 连通性 | 是否能追溯到出水口或泵站 | 是 / 否 |
| 数据来源与年份 | 竣工图、现场测量、数字化、推断 | as-built 2019 |
| 核实状态 | 未核 / 已核 / 现场确认 | |

现有系统已经在计算层做了这些标签，底座建设要把它们**前移到入库层**，并把「断头承接 20 公顷以上」「所需管径跳三倍以上」「几米缺口」这三条拓扑审计规则变成入库门禁：不通过的记录可以入库，但带标记，且自动生成核实工单。

### 4.3 L2 地形与环境层：DEM 是最大的单项缺口

没有 DEM，汇水区划分只能靠假设，二维淹没模型无从建立，低点识别只能靠井盖标高。建议一次性完成全市机载 LiDAR，0.5 米格网，垂直精度 ±10 厘米，同时产出 DSM、建筑高度与不透水率图。城市化快的片区两年复飞。这是整个底座里投入产出比最高的一项。

### 4.4 L3 观测层：现在是零，要从零建到能校准模型

详见第 5 节。原则是**先服务对账，再服务实时控制**：第一批站点的选址目标是让每场雨都能算出命中率与误报率，不是为了大屏。

### 4.5 L4 模型与状态层：状态量要能实时重算

- 排水图与承载雨强由底座在台账更新后自动重算，作为全网统一状态量供任何应用调用；对任意雨强的重算应在秒级完成。
- 水动力模型与世界模型在预测侧运行，底座负责给它**版本化的输入包**和接收**版本化的结果**。结果按 prediction_state 契约入库，节点、管段、出水口、二维网格四个粒度都留。
- 情景库统一管理设计雨、历史事件、气候情景，每个情景带年发生概率，供稳健优化加权。
- 校准记录表：每次模型校准用了哪些事件、参数改了什么、指标变了多少。

### 4.6 L5 决策与反馈层：让每条建议有生命周期

建议从生成到关闭经历：建议 → 人工确认（采纳/否决/合并）→ 立项 → 实施 → 竣工回写台账 → 效果评估（对账）。底座为这条链保留每一步的记录，并把「采纳/否决」回灌给下一轮排序。这一层现有系统的表结构已经具备（proposal、plan、verification），缺的是与 DMT 工单和项目管理系统的对接。

## 5. 感知建设方案

观测层现状为零：传感器台账 0 行、泵站遥测字段全空、无雨量与潮位时序。建设分三期，每期都以「能支撑什么决策」为验收。

| 期 | 时间 | 建设内容 | 数量（初步） | 支撑的决策 |
|---|---|---|---|---|
| 一期 补基线、建对账能力 | 0 至 12 个月 | 补测 61 个疑似漏登终点与 19% 缺标高管段；全市 LiDAR DEM；雨量站网加密；泵站 SCADA 接入；出水口潮位站；巡检 App 与 993 投诉积水点对接 | 雨量站按每 10 至 15 平方公里一站补到约 60 站（现 55 个 NCM 站位置需核实可用性）；103 台泵全部接遥测；潮位站 5 处；巡检 App 全员 | D1 可信、D5 首次对账 |
| 二期 关键节点水位与流量 | 12 至 30 个月 | 干管关键节点液位计；出水口流量或水位计；路侧积水水位标尺加摄像头；事件后无人机与卫星 SAR 影像流程 | 液位计约 200 点（按 49 个高潮易涝出水口汇水区与 61 个大终点上游优先）；出水口 50 点；积水摄像头 100 处 | D3 模型校准、D4 剩余风险实测化 |
| 三期 全覆盖与实时控制 | 30 至 60 个月 | 泵闸远程可控；蓄渗设施水位；边缘计算与实时预警；观测密度按对账误差热点动态加密 | 按二期对账结果定 | D2 事件前调度成为真触发 |

站点选址不按行政均分，按**对账价值**排：优先放在承载雨强最低的汇水区、高潮易涝的出水口上游、疑似漏登终点附近，以及历史投诉密集区。每期结束用对账指标（命中率、误报率、深度误差）检验站网够不够。

传输与存储：遥测走 ADM 现有 SCADA 主干或 NB-IoT；时序数据进时序库，保留原始值与质控值两份；影像与栅格进对象存储，元数据进目录。

## 6. 核心数据模型

围绕六个核心实体建模，其余表都挂在它们上面：

| 实体 | 关键字段 | 说明 |
|---|---|---|
| 资产 Asset | unitid、类型、几何、标高、质量标签、版本 | 管、节点、出水口、泵闸、蓄渗设施统一抽象，各类型有扩展表 |
| 网络版本 NetworkVersion | version_id、生成时间、拓扑校验结果摘要 | 每次台账变更生成新版本，所有计算引用版本号 |
| 情景 Scenario | 名称、雨强或事件、历时、重现期、潮位、年概率 | 设计雨、历史事件、气候情景 |
| 事件 Event | event_id、起止时间、雨量、潮位、预报、观测、对账结果 | 一场雨的全生命周期 |
| 干预 Intervention | 类型、目标资产、参数、成本、所属方案 | 九类干预，与模型输入一一映射 |
| 运行 Run | run_id、网络版本、情景、干预集合、结果引用、指标 | 预测侧与优化侧的每次计算 |

时序观测单独建表（站点、时间、变量、原始值、质控值、质控标志），与 Asset 通过站点关联；模型结果按运行与粒度分表，二维网格结果以栅格文件加索引存放。

### 7.1 质量规则（入库门禁）

| 规则 | 判据 | 不通过时 |
|---|---|---|
| 拓扑闭合 | 每段管两端都有节点，节点有类型 | 标记并生成核实工单 |
| 标高单调 | 上游管底不低于下游，坡度在 0.05% 至 10% | 标记「逆坡」或「过平」 |
| 管径不跳级 | 相邻下游管径不小于上游一半 | 标记「疑似连接错误」 |
| 终点必有出路 | 每一支最终到出水口、泵站或渗蓄设施 | 标记「断头」，超 20 公顷自动升为高优先级核实 |
| 基准一致 | 标高字段带基准码且可换算 | 拒绝入库 |
| 编码唯一 | unitid 全库唯一，与 SCADA、工单一致 | 拒绝入库 |

### 7.2 责任矩阵

| 数据域 | 数据所有方 | 更新触发 | 底座方职责 |
|---|---|---|---|
| 管网与设施台账 | ADM 资产部门 | 竣工、检修、核实工单关闭 | 门禁、版本、质量标签 |
| DEM 与用地 | DMT 测绘与规划 | 复飞、规划变更 | 派生不透水率与汇水区 |
| 雨量、潮位、预报 | NCM、港务 | 实时 | 接入、质控、事件切分 |
| SCADA 与积水观测 | ADM 运维、警务、市民渠道 | 实时、事件级 | 接入、编码对齐、事件归并 |
| 模型结果 | 预测侧 | 每次运行 | 契约校验、入库、对账 |
| 建议与方案 | 本系统与 DMT 决策方 | 每次运行、人工确认 | 生命周期记录、回灌 |

### 7.3 更新时效承诺

台账变更 30 天内入库并重算；观测实时入库，事件结束 72 小时内完成观测汇集与对账；预报每小时刷新；DEM 五年，重点区两年；费率与预算年度更新。

### 7.4 血缘与审计

每个数据产品记录上游来源、转换规则、生成时间与负责人；每条建议记录所依据的网络版本、情景、参数版本。任何数字都能在五分钟内回溯到源表与那一行。

### 7.5 安全与分级

管网几何与设施位置属于关键基础设施信息，按分级管理：原始台账与遥测限内网；派生的片区级指标可对外；对预测侧与优化侧的交换文件脱敏坐标精度按需降级。所有访问留痕。

## 8. 平台与技术要点

| 组件 | 建议 | 说明 |
|---|---|---|
| 空间数据库 | PostgreSQL + PostGIS | 延续现有 pipe 库的网络 schema，减少迁移 |

| 接口 | 三种 JSON 契约 + REST | prediction_state、whatif_request、whatif_result、event_observation |
| 目录与血缘 | 元数据目录 | 每个数据产品一页：来源、频率、质量、负责人 |
| 与现有平台关系 | 空间数据智能平台的数据层 | 底座作为平台的一个数据域，指标与语义层复用 |

## 9. 分期路线与成熟度指标

用六个就绪条件衡量底座成熟度，每期结束时对照检查。

| 期 | 交付 | 就绪条件目标 | 成熟度指标 |
|---|---|---|---|
| 一期 12 个月 | 基准统一、台账核实、DEM、雨量站网、SCADA 接入、对账流程首跑 | 验收标准已定义：就绪；物理基线可信：就绪；雨后回灌闭环：部分 | 拓扑可追溯率 39% → 90%；标高有效率 81% → 98%；对账事件 ≥ 3 场 |
| 二期 30 个月 | 液位流量站网、模型校准、剩余风险实测化 | 预测模型有观测校准：就绪；不确定性进入优化：就绪 | 命中率 ≥ 0.8、误报率 ≤ 0.3；情景年概率来自实测 |
| 三期 60 个月 | 泵闸可控、实时预警、观测动态加密 | 实施后有验证与运行规则：就绪 | 事件前调度真触发；方案效果有实测对账 |

## 10. 与现有系统的衔接

现有「会思考的排水系统」已经把 L4 的排水图与承载雨强、L5 的建议与方案、以及三种交换契约做出来了，并且在计算层实现了第 4.2 节的质量标签和第 7.1 节的三条拓扑审计规则。底座建设的第一步不是新建平台，而是：

1. 把计算层的质量标签与审计规则前移到台账入库门禁；
2. 把 61 个疑似漏登终点的核实作为一期第一项任务，这一项完成后系统的可追溯率会从 39% 跳升；
3. 用 LiDAR DEM 替换汇水面积假设，用 ADM IDF 替换雨强占位；
4. 接入泵站 SCADA 与雨量站，让第一场雨的对账跑起来。

这四件事做完，系统页面上的六个就绪条件会从「0 就绪、4 缺」变成至少「3 就绪」，承诺句从目标开始向保证靠近。

## 11. 风险与假设

- **跨部门数据授权**是最大风险：雨量与潮位在 NCM 和港务，SCADA 在 ADM 运维，投诉在警务与市民渠道。建议由 DMT 牵头签数据共享协议，本方案第 7.2 节的责任矩阵作为附件。
- **编码不一致**会让遥测接不上台账：先做一次 GIS 与 SCADA 的设施编码对照表，再谈接入。
- **DEM 与台账标高基准不一致**会让二维模型系统性偏差：一期第一件事是垂直基准换算表。
- 本方案中的站点数量、精度与时效都是**初步建议**，最终按一期对账误差调整；设计雨强、可接受积水深度等标准由 DMT 确认后生效。
