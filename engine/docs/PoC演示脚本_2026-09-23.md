# PoC 演示脚本（2026-09-23 演练版）

对着客户的九项议程（`Stormwater Hotspot Simulation_PoC_Agenda.docx`）走一遍：每项在哪一页、点什么、说什么、屏幕上会出现什么数字。所有数字来自 2026-09-23 的真机演练（`out/演练_2026-09-23_PoC/transcript.md`，15 问、deepseek-flash 规划器），不是排练稿里的估计。

## 0. 开场前 15 分钟

| 步骤 | 命令 / 动作 | 通过的样子 |
|---|---|---|
| 1 启动服务 | `python -m swbrain.serve --port 8766` | 日志出现「就绪：261,547 段」与「盘上缓存 …：N 条」，装载 **2.5–3 s** |
| 2 等预热 | 看日志 | 缓存命中时「预热完成：8 个情景，合计 0 s」；冷缓存要 **15 分钟**，所以别在演示前改模型层代码或重跑批处理 |
| 3 预热报告 | 浏览器打开一次 `/api/report?rp=10cc&lang=zh`，再打开 `&lang=en` | 首次 **约 100 s**，之后秒回。**必须提前点**，否则演示现场会干等 |
| 4 确认情景 | 控制台右上角重现期选到 **10 年 + 20% CC** | 顶栏显示「本页有 16 项假设」 |
| 5 智能体 | 抽屉里问一句「现在有多少积水点」 | 回答里注明规划器 `dsh` / 模型 `deepseek-flash`；不通则退到规则规划器，也能答 |
| 6 只开一个 Harness 标签页 | 如果要演 Harness Web UI（3080） | 同主机 6 条连接上限，开两个会卡死 |
| 7 把要演的情景各点一遍 | 顶栏依次切 10 年 + 20% CC、50 年、2024-04、2026-03，每个等它出数 | **必做**。切到决策时刻差得远的情景（设计情景约 200 min，两场实测雨约 765–770 min）会触发一次路况刷新，刷新后所有调度缓存作废，那一次要等 **30–90 s**。开场前走一遍，现场就都是秒回 |

**演示中不要做的事**：不要重启服务（缓存要重建）；不要改配置或模型层代码（会让盘上缓存整体作废）；不要在演示机上跑批处理；不要点「刷新路况」（那会换一个路况快照，所有情景的调度缓存跟着作废）。

## 1. 议程一 · 方法、判据与参数

**在哪**：控制台「数据与可信度」页 +「本体模型」页。
**说什么**：判据不是拍脑袋，每一条都能点开看逻辑与出处。
**演**：本体页 → 规则表（23 条）→ 点「应急等级」看到 WA-726-3 表 11-1 的出处；再点顶栏「本页有 16 项假设」。
**可以问**：「你们判一个点是不是 III 级、目标排干时限怎么定？依据是什么规范？」（演练 20 s，答出三条规则的完整逻辑与出处）
**屏幕上的数**：本体 14 对象 / 22 关系 / 23 规则 / 35 动作；假设 16 项（模拟 4、假设 4、占位 2、未核实 4、缺失 2）。

## 2. 议程二 · 降雨事件前中后

**在哪**：顶栏重现期切换 + 第三道页面的时间轴。
**演**：先问「预报三天后有 60 mm 的雨，相当于几年一遇？该用哪个情景准备？」（9 s）——它会算出年一遇、挑最贴近的情景、给预警等级与预置窗口，并**自动把控制台切到那个情景**。然后拖第三道的时间轴看积水随时间涨落。
**屏幕上的数**（10 年 + 20% CC，24 h 61.3 mm）：374 个点有积水过程（III 67 / II 249 / I 58）；客户清单共 845 个，其余 471 个没有过程线（87 个无管网或没匹配到管段，其余低于 100 m³ 下限）。

> **注意**：凡是问「预报 X mm」的问题都会切换当前情景。演示时要么提前说明「它会把控制台切过去」，要么问完再切回 10cc。

## 3. 议程三 · 样本热点：范围、退水时间、缓解前后

**在哪**：地图点开任一热点 → 单热点详情；或第三道页面的退水重演。
**演**：问「ADM-62 在当前情景下什么时候能退水？怎样最快？」（13 s，给自然退水 / 派泵 / 罐车 / 换管四条曲线与各自成本），再问「ADM-62 换大两级管径能不能不积水？」（20 s，缓解前后对比）。
**说什么**：同一个点，第三道（泵）和第一道（换管）的效果与代价能并排比。

## 4. 议程四 · ERP 资源优化（这项是重头）

**在哪**：第三道页面。
**演**：三目标切换（最快退水 / 平衡 / 最省钱）→ 资源占用表 → 甘特图 → 压力测试按钮 → 第二道的预置到位表。
**屏幕上的数**（10cc，决策时刻 210 min。2026-09-23 修正过一处大缺陷，见下）：

| 目标 | 费用 AED | 压住点数 | 泵 + 罐车 | III 级达标 |
|---|---|---|---|---|
| 最快退水 | 1,689,595 | 111 | 65 + 460 | 3 / 42 |
| 平衡 | **1,526,696** | 105 | 42 + 450 | 3 / 42 |
| 最省钱 | 646,353 | 71 | 26 + 246 | 2 / 42 |

> 费用取的是页面上那一列（v2 口径：台时 + 动员 + 人工 + 燃油 + 车公里 + 罐车台时 + 跨区工单），也就是求解器真正在优化的那个。接口顶层的 `cost.total_aed` 是 v1 口径（只有台时 + 动员），同一个方案会小三成。客户要是追问两个数为什么不一样，就按这个说；别把两列混着引。

> **这张表 09-23 与 09-24 各换过一次，旧数都不要再用**（作废的是 700,997 / 486,297 / 347,551 和 1,207,560 / 1,022,585 / 337,336 两版）。
>
> 09-23 修的是：求解器给「1.5 km 内没有排放去处」的点也派泵，而且按满额排量算——泵抽上来的水其实没地方排。修掉之后这些点只能靠罐车拉走。
>
> 09-24 修的是目标函数里两处基准不一致（详见 `docs/优化模型说明.md` §5）：收益项算的是增量（派了之后的积水小时减去不派的），延误罚却用绝对值，而「不派」这个选项根本不进目标、一分不罚。于是「派了也追不上目标时限」的点被系统性拒派——偏偏是水量大、优先级高的那批。修完之后压住点数 89 → 106，全网积水小时减少从 34.3% 提到 38.9%。

**必须主动讲的一件事**：三个目标费用差 **2.7 倍**（66.4 万 vs 180.6 万 AED），**全网加权积水时长只差 6.5%**。原因不是求解器有问题，而是第三道能管的就这么多：

| | 被派的点 | 全网 374 点 |
|---|---|---|
| 最快退水 | 112 点，积水时长少 74.6% | 少 39.3% |
| 平衡 | 106 点，积水时长少 75.4% | 少 38.9% |
| 最省钱 | 72 点，积水时长少 80.3% | 少 30.1% |

分诊说明其余的点（决策时刻 210 min，374 个点）：

| 分诊 | 点数 | 在哪个区 |
|---|---|---|
| 无需处置（已基本退水） | 141 | 三区都有 |
| **本片区没有管网数据，排放去处未知** | **87** | 艾因 49 + Dhafra 38 |
| **入流仍大于可派排量**（先封路疏散，雨峰后再派） | **61** | 三区都有 |
| **1.5 km 内无可接纳的排放去处** | **46** | 全在阿布扎比 |
| 可派泵（需接力排放） | 32 | 阿布扎比 |
| 可派泵 | 7 | 阿布扎比 |

> **这两行一定要分开讲，别合并。** 我们的管网台账只覆盖阿布扎比，艾因与 Dhafra 一个终点都没有，所以那 87 个点的排放去处**判不了**，系统按最保守办当成没有、只能罐车拉。而客户自己的热点清单标注艾因 139/184、Dhafra 120/155 是有管网的。要是把这 87 个说成「那里没有排水」，客户当场就能反驳。顶栏假设总账里有一条 `network_coverage` 专门写这件事。

也就是说：**还在积水的 233 个点里，只有 39 个能靠泵解决**，133 个得靠罐车一车 17 m³ 地拉，61 个连罐车都来不及。客户预案 A 的罐车池 476 辆，平衡目标一次用掉 **450 辆——几乎见底**。

> **客户一定会问「为什么要这么多罐车」，答案要分两半说。**
>
> 450 辆里 **362 辆（80%）派给艾因与 Dhafra** 的那 87 个点——那两个区我们没有管网数据，排放去处判不了，只能按最保守办。**拿到管网之后这个数会大幅下来。**
>
> 剩下 **88 辆**才是给阿布扎比那批真正查明 1.5 km 内没有排放去处的点。这 88 辆背后是实打实的管网缺口，**这才是第一道基础设施投资的理由**——别回避，但也别把前面那 362 辆算进来。

**预置**（橙级）：本系统建议 463 台，客户预案 A 计划 463 台，21 个驻地里 5 个计划低于需要；现场 check-in 数据还没有，所以标 **plan only**。

## 5. 议程五 · Agentic AI 指挥链、预警触发与自动提示

**演**：问「预报明天 80 mm，要发什么级别的预警？各角色该做什么？」——出等级、四个角色的分条提示、时间线（联络人是待填占位，要说明）。再演事中重规划：「现在是事件开始后 300 分钟，ADM-4 已退干、PA-016 泵坏了，重新排一下」——已出发的锁定、退干的释放、故障泵剔除、993 报案加权。
**说什么**：智能体只能做本体里声明的 35 个动作，没有自由 SQL、没有自由文件访问；每一步都记进动作日志。两个写动作（签发预警、登记观测）会写 `out/`，演示时可以说明但不必真发。

## 6. 议程六 · 样本输出与报告

**演**：顶栏「报告」按钮 → 自包含 HTML，浏览器里可另存或打印成 PDF；右上角切 EN 出英文版。
**注意**：**开场前必须预热过**（首次约 100 s）。英文版已无中文残留（2026-09-23 修）。

## 7. 议程七 · 全面实施与三区

**说什么**：ADM 有管网台账（26 万段），所以第一道的筛查与建议只在 ADM 成立；AAM（艾因）与 DRM（Dhafra）目前只有热点清单与预案 A 资源，没有管网，因此那两区只有第二、三道（预置与调度），第一道要等 DMT 给管网数据。
**屏幕上的数**：10cc 下 374 个有过程线的点里 ADM 240 / AAM 87 / DRM 47。

## 8. 议程八 · 数据缺口

**演**：顶栏「本页有 16 项假设」点开；再问「993 报案和承包商 check-in 现在接进来了吗？还缺哪些数据？」
**要的东西按优先级**：① 两场实测雨（2024-04、2026-03）的逐点积水记录 → 命中率、漏报、真实复发率；② 市区各站雨量（NCM）→ 替换两处缺省假设；③ 993 与 check-in 的接口地址或推送；④ 桥梁限重台账、承包商服务边界；⑤ 合同费率表；⑥ AAM / DRM 的管网数据。契约与导入器都已就绪（`exchange/schemas/`、`python -m swbrain.episodes_import`），文件到了当天就能进系统。

## 9. 议程九 · 结论与下一步

**演**：压力测试——「如果雨比预报大一档，现在这套方案还差多少泵？」
**说什么**：系统给的不是「不会淹」的承诺，是三件能检验的东西：分年实施的方案（带成本与达标年限）、事件前的预置与事中的调度单、以及每一步的依据和假设。

## 附：出问题怎么办

| 症状 | 处理 |
|---|---|
| 智能体不回话 | 抽屉里会显示规划器；模型不通会自动退到规则规划器，仍能答常见问题。实在不行走页面演示，功能一样 |
| 某个操作转圈很久 | 长求解已经在子进程里跑、页面轮询任务号，其他页照常点。等秒数显示在按钮上 |
| 服务真的挂了 | 重启只要 3 秒装载（缓存还在），不要清 `out/cache` |
| 客户问「这个数是真的吗」 | 点顶栏假设总账，逐条有来源与替换办法；模拟的就说模拟 |
| 客户问历史某场雨 | 逐点记录还没有，系统会明说是「推演估计」；不要说成实测 |
| 一个问题问下去很久没回 | 多半是模型自己串了十几个动作（见上表）。等就是了，页面不受影响；下次把问题问窄 |
