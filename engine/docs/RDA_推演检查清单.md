# RD-A 推演检查清单（2026-10-31 这次推演踩过的坑）


用户 2026-10-31 要求：把这次推演中出过的错记下来，下次推演（新汇水区、新数据）不要重犯。

**推演前（脚本和数据）**
1. 写推演脚本前先和用户确认 L1/L2/L2planned 含哪些数据，见 [[confirm-states-before-scripts]]；状态字段先核对真实字段名（dbf 会把 ASSET_STAGE 截成 ASSET_STAG），别凭印象。
2. 出水口、数据口径（谁用全市数据、谁用汇水区数据）先问清，不要自己推断；出水口边界按 F 系列固定 1.3 m + 拍门。
3. 容器环境变量要核对**真的传进推演容器**：这次 DTM_PATH 只在 check 里显示，start 漏传，三台实际都用 5 m 地形。启动后必须在日志里看到「DTM：…0.5 m」才算数。地形要写进旧结果指纹。
4. 三台服务器地形、镜像、engine 版本必须一致；更新包给三台用同一份。
5. 旧测试结果只「挪开」不删（_old_test_<时间>/），页面旧记录先备份再删。
6. macOS 打包用 COPYFILE_DISABLE=1 / --no-xattrs，别带 `._*` 文件，否则服务器安装脚本会出错。
7. 更新包解压后的文件权限：`docker cp` 会把 NAS 上的权限原样带进容器（660、组 1014），页面进程读不了，接口 404。拷进容器后要 chown root:root + chmod 644。

**入库和页面（最容易出问题的地方）**
8. 页面里有按 extent 写死的逻辑：extent=='RDA' 会读固定的 AECOM 数据；engine 交付入库时 extent 要设为区域标题（RD-A），积水点和热点覆盖要用自己的 npz 现算。
9. 页面上有按「全市 #1068」写死的口径（L2 排掉 35%、L1 = L2÷65%，在 LevelPanel.vue）：区域推演要用 cityGe=false 走模型真值，不能让它造出假的 L1 数。新增区域前先搜页面里写死的「全市」「City-wide」「L2_REMOVES」。
10. 多态必须是**同一个仿真**（一个交付根 + 多个态目录，job_id 不带态后缀），不能拆成多个 job。
11. ponding_ge.json 的键必须是页面态 key（L1 / L2 / L2+planned），不是内部名 L2planned，否则卡片不出。
12. 页面「雨水管网」开关原来请求 /api/network/mains（全市，后端没有这个接口，404）：区域推演要在交付根写 pipes.geojson，由 /api/simulations/{id}/pipes 提供。已入库的旧结果要补写并 chmod。
13. 缺参数的设备（临时泵、Geocell、Planned 泵）不进模型但照常跑；页面要标「未建模（数据缺参数）」并列出各态新增设备（FacilityList.vue），别让用户以为算进去了。L2 与 L1 结果相同是预期。

**入库流程**
14. 交付目录还在跑时不能入库（目录不存在会失败）；先 `ls deliveries/<job_id>` 和 status 确认，再 `./app.sh import <job_id>`。多条命令写进一行或脚本里，用户不想一条条敲。
15. 更新包放哪、怎么回退要写进脚本头注释；更新后让用户确认的点逐条列出（设备清单标记、三态总积水量一致、管网可点）。

**汇报习惯**
16. 没验证的要明说（比如本机没有 geopandas，管线生成只做了语法检查）；用户给的口径如果后来发现不一致（如 1068 没有 L1 排水卡片），以用户核对后的为准，别硬套。

**Why:** 这些都是 2026-10-31 RD-A 9 场景推演里实际发生并返工过的问题。
**How to apply:** 下一次推演（新汇水区或重算）开始前逐条过一遍；相关背景见 [[rda-9-scenarios-plan]]。
