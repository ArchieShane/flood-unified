# 会思考的排水系统（swbrain）· 系统架构设计

版本 v1.0 · 2026-10-02 · 对应代码提交 `58ff12d`（分支 `c1-l1l2-catchments`）

本文是整个系统的架构总览：分几层、每层做什么、数据怎么流、智能体怎么接入、身份与安全怎么做、怎么部署。
各部分的细节另有专题文档，文中在相应位置注明。

---

## 1. 系统定位

对阿布扎比市（ADM）雨水管网做「控-监-测」式的智能研判：从台账与管网图算出每段管、每个汇水区、每个片区的排水状态，
给出**在什么时间、什么位置、加或调什么设施**的建议，每条带前后对比、优先级、置信度、依据与假设，等人确认。

系统按**三道防线**组织：

| 防线 | 回答的问题 | 主要模块 |
|---|---|---|
| 第一道 · 基础设施建设 | 建什么、先建哪个、几年达标、建完还剩什么风险 | `decisions` · `whatif` · `standards` · `verification` |
| 第二道 · 预报后预置 | 预警来了，泵和人先放到哪里 | `dispatch.preposition` · `alerts` |
| 第三道 · 临时应急调度 | 积水已经出现，派几台泵、谁先去、多久退水 | `dispatch2`（MILP + 滚动 + 鲁棒）· `travel` · `traffic` · `recession` |
| 防线 2+ · 热点群一二维 | 某个热点群在各设施状态下积水减了多少 | `tools/c1_pipeline.py`（SWMM + ANUGA 双向耦合） |

**分工**：本系统是优化侧（what-if）。预测侧（城市内涝世界模型）在另一个项目里，两边靠 `exchange/` 下的 JSON 契约交换；
没有预测结果时本系统用曼宁 + 推理公式粗算兜底，并在结果里标明。

**设计原则**

- **源库只读**：客户 PostGIS 库会话级只读，系统从不写源库。
- **不编数字**：智能体只能通过本体动作取数；模拟、假设、占位的输入在载荷与回答里逐条标出（假设总账）。
- **可追责**：每个本体动作、每次管理操作、每个计算任务的状态变化都落日志，统一身份下记主体号。
- **长任务不挡路**：调度求解走子进程，一二维计算走独立执行进程与 docker 容器，服务本身始终可响应。

## 2. 总体架构

六层，自上而下调用，下层不知道上层：

| 层 | 组成 | 与下层的接口 |
|---|---|---|
| 交互层 | 控制台 `console/`（地图、三道防线页、防线 2+、对话抽屉、本体页）；管理端 `/admin.html`；Harness 原生 Web UI（本机 3080，局域网经 3081 代理） | HTTP `/api`（54 个接口）；Harness 经 MCP（stdio） |
| 服务层 | `serve.py`（HTTP、身份、口令）· `routes.py`（接口表）· `state.py`（状态）· `artifactcache`（落盘缓存）· `jobs`（求解子进程）· `dsh_lanproxy` | 调智能体层，或页面直接调本体动作 |
| 智能体层 | 主智能体（分派）→ 调度研判 / 一二维计算 / 报告交付 / 数据质检 / 自建；规划器 DeepSeek Harness → 直连大模型 → 规则 | **只经** `Runtime.act` 与对象查询 |
| 本体层 | `schema.py`：对象类型 17 · 关系 31 · 规则 28 · 动作 49；`runtime.py`：`Runtime.act`（权限、校验、审计的唯一出口） | 调模型层函数、读状态 |
| 模型与计算层 | 图与水力（graph · hydraulics · indicators · networkflood）；决策（decisions · whatif · standards · verification · lifecycle）；调度（dispatch · dispatch2 · resources · travel · traffic）；一二维（c1_pipeline → docker `anuga-swmm:1.0`，computejobs 排队） | 读数据层 |
| 数据层 | 客户源库（只读）· 本地输出库 `sw_brain` · `out/state`（parquet / npz）· `exchange/`（预测、请求、结果、六类外部源）· 客户文件（GDB、DTM、水力模型） | — |

当前规模：Python 84 个模块、约 2.4 万行；66 个测试文件，525 个用例；54 个 HTTP 接口；49 个本体动作。

**本系统的核心设计**：智能体不直接碰数据、模型或文件，它看到的只是本体对象，能做的只是本体动作；
本体层（第 3 节）与智能体层（第 4 节）之间只有一个接口 `Runtime.act`。下面两节是本文重点。

## 3. 本体层：智能体的「世界」与「手」

### 3.1 本体的四类声明

本体全部声明在 `swbrain/ontology/schema.py`，以「积水点」为核心（完整清单见 `docs/本体模型.md`）：

| 声明 | 数量 | 内容 | 对智能体意味着什么 |
|---|---|---|---|
| 对象类型 | 17 | 积水点 FloodPoint、积水状态 FloodState（随情景）、情景、管段、片区、泵 / 罐车、驻地、派单、工程建议、世界模型推演核、预警单、现场观测、降雨事件、积水经历、设施、汇水区、分析范围 | 它能「看见」的东西；每类有主键、属性、是否随情景 |
| 关系 | 31 | 如 积水点 → 所在汇水区、积水点 → 派单 → 泵、积水点 → 历次经历 | 它能「顺着走」的路 |
| 规则 | 28 | 推导 16、校验 7、触发 5；每条有适用对象、逻辑说明、出处 | 对象上的判定（如分级、是否该派泵），可解释 |
| 动作 | 49 | 只读 40、会写数据 9 | 它唯一能「做」的事 |

会写数据的 9 个动作：`traffic_status`（刷新路况）、`update_episode`、`close_point`、`set_proposal_status`、`open_event`、`issue_alert`、`record_observation`、`hydro_submit`、`report_submit`。
写的都是系统自己的记录（`out/`、`exchange/`、任务队列），**没有任何动作写客户源库**。

### 3.2 一个动作声明了什么

每个动作是一条 `ActionType`，这些字段同时服务于执行、权限、规划与界面：

| 字段 | 用途 |
|---|---|
| `api`、`zh` / `en`、`desc_zh` / `desc_en` | 名字与说明：生成工具说明、系统提示、控制台文字 |
| `params`（名称、类型、枚举、上下限、必填、缺省） | 生成工具的输入模式（JSON Schema）；`Runtime.validate` 按它校验 |
| `side_effect` | `none` = 只读；非空 = 会写数据，写明写到哪里。决定只读入口能不能调、要不要「明确要求」 |
| `intents`、`examples` | 规则规划器的意图关键词；控制台示例问题；工具说明里的例句 |
| `owner` | 归属哪个智能体（`dispatch` / `hydro` / `report` / `qa`）：决定谁能看到、谁能调 |

每个动作在代码里对应两个方法：`_act_<api>(P)` 取数 / 计算，返回结果与界面联动提示（`_ui`）；
`_sum_<api>(结果, P, 语言)` 生成中、英两份小结。**回答里的数字来自小结，小结来自结果**，智能体没有别的取数途径。

### 3.3 唯一出口：`Runtime.act` 的执行管线

不管调用来自哪个智能体、哪个规划器、哪条入口（控制台、MCP、命令行），最终都落到 `Runtime.act(api, params, actor, lang)`
（`swbrain/ontology/runtime.py`），依次做：

```
Runtime.act(api, params, actor)
 ① 动作存在？                         ── 否 → 拒
 ② 管理端停用了它 / 它的主人智能体停用了？  ── 是 → 拒（控制台页面直接调的除外）
 ③ 调用方是自建智能体（actor = agent:<id> / dsh:<id>）？
      该智能体停用了 / 动作不在它挑的那组里？ ── 是 → 拒
 ④ 统一身份：取「发起这次对话的人」
      只读入口 且 动作会写？              ── 是 → 拒
      写动作 → 现查平台会话（撤销立即生效）
      此人没有该动作要的职能？             ── 是 → 拒（智能体调的也一样，不因为是智能体就放行）
 ⑤ 参数校验（类型、枚举、上下限、必填）    ── 不过 → 拒
 ⑥ _act_<api>(P) → 结果 + ui 提示；_sum_<api> → 中英小结
 ⑦ 写一行动作日志 out/ontology_actions.jsonl（时间、actor、动作、参数、成败、耗时、小结、副作用）
 → 返回 {ok, result, summary_zh, summary_en, ui, console_link, side_effect, ms}
```

- 被拒也记日志，`actor` 里带上是谁被拒（`sdip:<主体号>/dsh:hydro` 这样的形式）。
- `actor` 标签是追责链：`sdip:2102/agent:hydro` = 主体 2102 经一二维计算智能体调的；`sdip:harness-web/dsh:dispatch` = 原生 Web UI 的只读身份。

### 3.4 一份声明，多处自动跟上

本体声明是唯一来源，下面这些都由它**生成**，不另写：

| 生成物 | 生成处 |
|---|---|
| 大模型的工具清单与输入模式 | `ontology/agent.py` `LlmPlanner.tools`（直连大模型）；`mcp_server.py` `tool_list`（DeepSeek Harness 经 MCP） |
| 智能体的系统提示（对象类型、关系、规则说明） | `LlmPlanner.system_prompt`；`mcp_server.instructions`（Harness 拼进它的系统提示） |
| 规则规划器的意图识别 | `RulePlanner` 按动作的 `intents` 打分 |
| 控制台示例问题、本体页 | `/api/ontology` |
| 文档表格 | `python -m swbrain.ontology --doc` |
| 一致性自检 | `python -m swbrain.ontology --check`（每个动作都有 `_act_` / `_sum_`、归属合法、参数合法） |

所以「给智能体加一项能力」= 加一个动作声明 + 两个方法（第 4.9 节），工具、提示、文档自动带上。

## 4. 智能体层：多智能体架构与本体集成

### 4.1 组成

| 智能体 | id | 名下动作 | 规划器（按序降级） | 职责 |
|---|---|---|---|---|
| 主智能体 | `orchestrator` | 无 | 大模型分派（`delegate` 工具）→ 规则分派 | 判断问题交给谁（最多两个）、汇总回答、记轨迹；自己不调业务动作 |
| 调度研判 | `dispatch` | 41 | DeepSeek Harness → 直连大模型 → 规则 | 三道防线：积水点何时退水、什么手段最快、派几台泵、全局与单点最优之差、预警、生命周期 |
| 一二维计算 | `hydro` | 4 | 直连大模型 → 规则 | 热点群一二维各情景 / 各态结果、计算进度、提交计算申请（含快速验证） |
| 报告交付 | `report` | 2 | 直连大模型 → 规则 | 交付目录与报告在哪；申请重出交付 |
| 数据质检 | `qa` | 2 | 直连大模型 → 规则 | 数据与环境齐不齐、各态结果质检 |
| 自建智能体 | 管理端起名 | 从现有动作里挑 | 直连大模型 → 规则 | 管理员按需组合（不能造新动作） |

代码位置：注册表 `swbrain/agents/registry.py`；主智能体与专业智能体规划 `swbrain/agents/orchestrator.py`；
调度研判 `swbrain/ontology/agent.py`；一二维 / 报告 / 质检的动作实现 `swbrain/ontology/actions/hydro.py`；
Harness 接入 `swbrain/dsh_bridge.py`、`swbrain/mcp_server.py`。

### 4.2 一次对话的完整链路

```
用户在控制台对话抽屉提问 ──► POST /api/agent（带登录会话）
  └─► 主智能体 MultiAgent.chat
        ├─ 分派：大模型调 delegate(agents, reason)；失败 → 按领域词 + 意图词打分
        │        理由写进轨迹；都没命中 → 调度研判兜底
        ├─► 专业智能体（hydro / report / qa / 自建）
        │     规划器：大模型（工具 = 自己名下、没停用的动作）→ 规则（抽情景 / 态 / 热点，按意图挑动作）
        │     └─► Runtime.act(动作, 参数, actor="agent:<id>")
        └─► 调度研判 Agent.chat
              ├─ DeepSeek Harness（SDK 运行时）──MCP──► mcp_server ──HTTP /api/action──► Runtime.act(actor="dsh:dispatch")
              ├─ 失败 → 直连大模型 LlmPlanner ──► Runtime.act(actor="llm")
              └─ 失败 → 规则 RulePlanner ──► Runtime.act(actor="agent")
  ◄── 汇总：回答 + 每步动作（参数、成败、小结、耗时）+ ui 联动 + 规划器与降级说明
  ──► 控制台：显示回答与结果卡片，按 ui 提示切情景 / 打开详情 / 地图高亮
  ──► 轨迹 out/agents/sessions.jsonl（问题、分派理由、各智能体步骤、回答、耗时）
```

### 4.3 分派规则（主智能体）

- 每个专业智能体有一组**领域词**，至少命中一个才会分给它；它名下动作的意图词只加分。这样「检查井」「调度结果」这类说法不会被抢走。
- 一句话同时命中两个智能体的核心领域词（如「算完了吗？质检过了没有？」），两个都分，最多两个。
- 情景名（模型版 / M61 / R61…）只算上下文，单靠它不构成去处；都没命中交给调度研判。
- 领域词可在管理端改（存 `out/agents/overrides.json`）。

### 4.4 三种规划器，同一套动作

| 规划器 | 何时用 | 工具 / 依据 | 特点 |
|---|---|---|---|
| DeepSeek Harness（dsh） | 调度研判；有 `DEEPSEEK_API_KEY`（或配置的其他供应商）且装了运行时 | 经 MCP 拿本体动作 + 通用工具；系统提示由本体生成 | 真正的智能体运行时：多步推理、子智能体、workflow 编排 |
| 直连大模型 `LlmPlanner` | Harness 不可用；或专业智能体 | 本体动作做成工具（调度研判另带 取对象 / 查对象集 / 沿关系走） | 最多 6 步工具调用；工具清单外的名字一律拒 |
| 规则 `RulePlanner` | 没有密钥或大模型不可达 | 动作的 `intents` 关键词 + 实体抽取（积水点编号、情景、雨量、态…） | 确定性、可审计、断网可用；回答由动作小结拼成 |

降级逐层发生，每一步在回答的 `note` 与轨迹里注明用的是哪个规划器、为什么降级。
三种规划器调的是**同一批动作、同一个 `Runtime.act`**，所以换规划器不会换口径。

### 4.5 DeepSeek Harness 与本体的集成（MCP 薄桥）

```
控制台对话 ──► dsh_bridge.DshBridge ──► dsh SDK 运行时（profile sdk，长驻子进程）
原生 Web UI ──► dsh Web（profile web，127.0.0.1:3080，四个预设 = 四个智能体）
                         │  每个预设一份 MCP 配置：SWBRAIN_OWNER / SWBRAIN_ACTIONS / SWBRAIN_READONLY
                         ▼
              swbrain.mcp_server（stdio，JSON-RPC 2.0）
                 tools/list ← 由本体声明生成（只列该智能体的动作 + get_object / search_objects / follow_link / ontology_overview）
                 instructions ← 由本体声明生成（对象类型、规则、工作方式）
                 tools/call ──HTTP──► 排水智能体服务 /api/action、/api/object、/api/objects
                                        └─► Runtime.act（同一个出口）
```

- **薄桥**：`mcp_server` 不装载任何管网状态，只把调用转发给正在运行的服务，启动几十毫秒；数字与控制台同源、同缓存。
- **桥这层先拦一次**：不属于该智能体的动作、只读入口里会写的动作，在桥上就拒，不只靠客户端不列出来。
- **身份穿透**：统一身份下，控制台对话开始时服务签一张短期**委托凭据**写到文件，桥调回服务时带 `Authorization: Bearer`，
  服务据此还原成发起对话的人、按他的职能判；对话结束删掉。原生 Web UI 分不出是谁在用（dsh 的 MCP 请求头是静态配置），所以那条入口只读。
- 预设由 `agent/dsh/presets/` 模板渲染到 `out/dsh_home*/.agent-presets/`；自建智能体自动多一份预设。

### 4.6 权限：四道闸

一个智能体想调一个动作，要依次过：

| 闸 | 在哪判 | 管什么 |
|---|---|---|
| ① 看得见 | 工具清单生成（`LlmPlanner.tools` / `mcp_server.tool_list`） | 只列它名下（或自建智能体勾选）且没停用的动作；看不见就调不到 |
| ② 调得动 | MCP 桥 + `LlmPlanner` 工具名校验 + `Runtime.act` ②③ | 不在清单里、别的智能体的、被停用的，一律拒 |
| ③ 该不该写 | 申请类动作的守卫（`orchestrator` guard）；工具说明里写明「只在用户明确要求时调用」 | 话里没明确说「提交 / 申请 / 重算」就不许调 `hydro_submit` / `report_submit` |
| ④ 人有没有权 | `Runtime.act` ④（统一身份） | 按**发起人**的职能判：`SWBRAIN.VIEW / FIELD / ALERT / PLAN / ADMIN / FEED`；写动作前现查平台 |

长时计算再加一道：申请只进待批准队列，**管理员批准后**才执行（第 6 节）。

### 4.7 两条入口

| | 控制台对话抽屉 | Harness 原生 Web UI |
|---|---|---|
| 地址 | `http://<主机>:8766/` 顶栏「智能体」 | 抽屉里「在 Harness 打开」；本机 `127.0.0.1:3080`，局域网管理员经 `3081` 代理 |
| 分派 | 主智能体自动分派 | 不分派：预设下拉自己选（四个预设对应四个工作智能体） |
| 身份 | 平台主体号（委托凭据穿透到 MCP） | 只读共享身份 `sdip:harness-web` |
| 能做什么 | 读 + 写（按职能） | 只读（写动作在 MCP 桥被拒） |
| 子智能体 / workflow | 开着 | 开着（`agent/dsh/web.patch.yml`） |

局域网入口：dsh 自身拒绝监听局域网（它能执行代码），服务里的反向代理 `swbrain/dsh_lanproxy.py` 只放管理员、校验来源、
把 Host / Origin 改写成回环地址再转发，WebSocket 原样转发；dsh 自己的一次性 token 照常要。

### 4.8 可观测与审计

| 记录 | 位置 | 内容 |
|---|---|---|
| 动作日志 | `out/ontology_actions.jsonl` | 每次 `Runtime.act`：时间、actor（含主体号）、动作、参数、成败、耗时、小结、副作用 |
| 对话轨迹 | `out/agents/sessions.jsonl` | 每问一行：分派与理由、各智能体步骤、回答、规划器、耗时；管理端「会话」页可查 |
| 管理审计 | `out/agents/admin_audit.jsonl` | 登录、改配置、新建 / 删除智能体、批准 / 驳回 / 暂停 / 恢复 / 取消计算、局域网打开 Harness |
| 计算任务 | `out/agents/jobs/<id>.json` / `.log` | 申请人、步骤、每次状态变化（谁、何时）、执行日志、结果 |

已知限制：Harness 派出的子智能体与主智能体在动作日志里记同一个身份（dsh 的 MCP 调用没有元数据通道），要追到子会话需另写 dsh 插件。

### 4.9 扩展

- **加一个动作**：`schema.py` 加 `ActionType`（含 `owner`）→ `runtime.py` 或 `actions/*.py` 加 `_act_` / `_sum_` → 跑 `--check` 与测试。工具、提示、文档自动跟上。
- **加一个智能体**：管理端「＋ 新建智能体」，起名、写职责、给分派关键词、从现有动作里勾一组；即时生效，Harness 自动多一份预设。新能力仍要先加动作。

## 5. 模型、数据与服务层

### 5.1 模型与计算层

| 组 | 模块 | 做什么 |
|---|---|---|
| 图与水力 | `extract` · `graph` · `hydraulics` · `indicators` · `networkflood` | 只读取数；定向建图、沿流向累加；曼宁满管流 + 推理公式；管段 → 汇水区 → 片区状态；全网溢流路由 |
| 第一道 | `decisions` · `whatif` · `standards` · `verification` | 十一类建议；干预集合评估、预算内组合、排期、按标准达标分期、剩余风险；就绪条件与验证协议 |
| 第二、三道 | `dispatch` · `dispatch2` · `resources` · `travel` · `traffic` · `recession` · `lifecycle` | 预置选址；分派 MILP（HiGHS）+ 滚动窗口 + 鲁棒期望；时变路网行程；退水重演；积水点生命周期 |
| 防线 2+ | `tools/c1_pipeline.py` · `docker/anuga-swmm` | 一维 SWMM 5.2 与二维 ANUGA 双向耦合；四个设施状态（L1 / L2 / L2+planned / L2+suggested）；后处理与交付 |

优化模型详见 `docs/第三道防线优化调度方案设计.md`、`docs/优化模型说明.md`；可信度边界见 `docs/可信度说明.md`。

### 5.2 数据层

| 数据 | 位置 | 读写 |
|---|---|---|
| 客户源库（PostGIS：pipe / makani / liveability / flood） | 客户服务器 | **只读**（会话级） |
| 本地输出库 `sw_brain`（schema `swbrain`） | 本地 PostGIS | 写：运行、状态、建议、方案 |
| 运行状态 `out/state/`（parquet / npz，约 26 万管段）+ `manifest.json` | 本地 | `swbrain.run` 批处理生成，服务装载 |
| 交换契约 `exchange/`（预测、请求、结果、六类外部源，JSON Schema） | 本地 | 与预测侧、外部系统交换 |
| 客户文件（管网 GDB、5 m DTM、22 个水力模型、Parsons 交付） | `config.toml [data]` 指向 | 只读，不入库 |
| 一二维工作目录 | `SWBRAIN_SWMM_WORK`（纯英文路径） | 计算读写 |

### 5.3 服务层

- `serve.py`：HTTP（IPv4 + IPv6）、身份与口令、静态控制台；`routes.py`：54 个接口的路由表，`GET /api` 自描述；`state.py`：状态装载与编排。
- `artifactcache`：情景上下文与调度载荷按「代码 + 配置 + 状态」指纹落盘，重启几十秒可用。
- `jobs`：调度求解（60–110 s）走子进程，`?async=1` + `/api/jobs/<id>` 轮询，求解期间其他接口照常响应。
- 精简模式：没有运行产物时也能起服务，C1 结果页与管理端计算队列可用。

## 6. 长时计算：申请 → 批准 → 执行

一二维计算单态要几小时到一天、占满 CPU，所以智能体只能申请（`swbrain/agents/computejobs.py`）：

```
智能体 hydro_submit / report_submit ──► pending（out/agents/jobs/<id>.json）
管理端「批准」──► 独立执行进程（与服务脱离，重启服务不打断）
    └─► 等队列外的计算让出机器 ──► tools/c1_pipeline.py（docker 容器 c1pipe_<情景>_<态>）
    └─► 写回 done / failed（快速验证附判定摘要）──► 自动接上下一条已批准的
```

| 环节 | 规则 |
|---|---|
| 类型 | 计算 / 后处理与交付 / 准备中间数据 / 快速验证（合成算例约 2 分钟、14 项判定） |
| 批准 | 有管理权限即可批，含自己提交的；提交人与每次状态变化都留痕 |
| 并发 | 同时只跑一条；命令行起的一二维容器在算时也先等（暂停着的不挡） |
| 进度 | 查询时读模型日志尾部：算到几小时、百分比、淹没面积、最深、剩余时间粗估 |
| 掉线 | 执行进程不在又没写回 → 标失败并注明 |
| 控制 | 暂停 / 恢复 = `docker pause` / `unpause`；取消 = 停容器 + 结束进程树 |

已知限制：不能断点续算（docker 或机器重启后要从头算）；任务文件未加锁。

## 7. 身份与安全

| 方面 | 做法 |
|---|---|
| 身份模式 | `shared_key`（缺省：访问口令 + 管理员口令，分不出人）或 `sdip`（统一身份：平台账号登录，按职能判，日志记主体号） |
| 职能 | `SWBRAIN.VIEW` 查看分析 · `FIELD` 现场登记 · `ALERT` 签发预警 · `PLAN` 工程建议 · `ADMIN` 系统管理 · `FEED` 外部源推送 |
| 智能体的权限 | 按发起人判，智能体本身不提权；写动作前现查平台会话，撤销立即生效 |
| 跨站防护 | 带会话 cookie 的写请求要 Origin 精确等于本服务；局域网代理同样校验 |
| 密钥 | 大模型密钥、平台客户端密钥只走环境变量；口令只在 `config.toml`（不入库）；日志里口令打码 |
| 源数据 | 客户源库只读；客户文件不入库 |
| 网络 | HTTP，仅限可信局域网；要出网先上反向代理与 HTTPS（`[serve].tls_cert` / `tls_key` 已支持） |
| 数据出境 | 规划器缺省走云端模型，提示词含热点名称与数字；可换本地或获批端点（`[agent.dsh].provider`），由 DMT 按数据分级决定 |

## 9. 质量保证

- 测试：66 个文件 525 个用例（合成夹具，约 30 秒）；真机集成测试 `SWBRAIN_INTEGRATION=1`；本地检查 `scripts/ci.ps1`（测试 + 前端语法 + 本体自检 + 配置漂移）。
- 换机器先跑快速验证：`python tools/c1_pipeline.py selftest`；安装自检 `python -m swbrain.doctor`。
- 本体自检 `python -m swbrain.ontology --check`；配置漂移 `python -m swbrain.configcheck`。
- 假设总账 `/api/assumptions`：控制台顶栏「本页有 N 项假设」，逐条列出模拟 / 假设 / 占位的输入及替换方法。

## 10. 已知限制

1. Harness 子智能体的调用与主智能体记同一身份；原生 Web UI 只读。
2. 一二维计算不能断点续算；计算队列文件未加锁。
3. 单进程服务、HTTP 明文，适合可信局域网与值班试用，不适合 7×24 多用户对外运行。
4. 多处输入仍是模拟或假设（资源、路况、承包商等），等客户数据替换。
5. 只在 Windows 11 上验证过。
