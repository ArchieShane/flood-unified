## 1. 一句话

智能体**只有一双手**：本体的动作（Action Type）。它看得见的是对象与关系（本体声明），做得到的是动作；
每个动作声明了参数、前置条件、副作用与**归属哪个智能体**，执行与判定集中在 `Runtime.act`（`swbrain/ontology/runtime.py`），
每一次调用都进 `out/ontology_actions.jsonl`（时间、谁、什么动作、参数、成败、耗时、小结、副作用）。

```
用户一句话
  └─► 主智能体（分派）
        └─► 某个专业智能体 ──► 规划器（dsh / 大模型 / 规则）
              └─► Runtime.act(动作, 参数)   ← 唯一的出口：权限、校验、审计都在这里
                    └─► 结果 + 中英小结 + ui 提示 ──► 回答 + 控制台联动
```

## 2. 为什么本体是唯一的出口

| 要求 | 本体怎么满足的 |
|---|---|
| 说给客户听的名词要稳定 | 对象类型与关系是声明出来的（`schema.py`），不是各模块自己的字典 |
| 智能体不许编数字 | 它没有别的取数途径：动作是唯一的，动作返回什么它就说什么 |
| 同一件事不许有两种口径 | 控制台各页、接口、智能体走的都是同一批动作与缓存 |
| 能追责 | 每个动作按「发起人 + 动作 + 参数」落一行日志；写动作另有副作用标注 |
| 权限能收紧 | 动作归属智能体、职能另有一层（统一身份），两层都在 `Runtime.act` 里判 |

**动作与智能体的关系是「归属」不是「复制」**：`schema.py` 里每个 `ActionType` 有一个 `owner`，
没标的缺省是 `dispatch`。当前 49 个动作的归属：

| 归属 | 动作数 | 会写数据的（9 个里有 9 个） |
|---|---|---|
| `dispatch` 调度研判 | 41 | `traffic_status(refresh)`、`update_episode`、`close_point`、`set_proposal_status`、`open_event`、`issue_alert`、`record_observation` |
| `hydro` 一二维计算 | 4 | `hydro_submit` |
| `report` 报告交付 | 2 | `report_submit` |
| `qa` 数据质检 | 2 | —（两个都只读） |

本体规模（随声明自动生成，改了就重跑 `python -m swbrain.ontology --doc`）：**对象类型 17、关系 31、规则 28、动作 49**。

## 3. 五个智能体

| 智能体 | id | 规划器 | 名下动作 | 管什么 |
|---|---|---|---|---|
| 主智能体 | `orchestrator` | 大模型分派（`delegate` 工具）→ 规则 | 无 | 判断问题该给谁（最多两个）、汇总回答、记轨迹；自己不调业务动作 |
| 调度研判 | `dispatch` | DeepSeek Harness → 大模型 → 规则 | 41 | 三道防线：积水点什么时候退水、用什么手段最快、派几台泵、全局调度与单点最优的差、预警、汇水区、生命周期 |
| 一二维计算 | `hydro` | 大模型 → 规则 | 4 | 热点群一二维（SWMM + ANUGA）各情景 / 各态的结果、计算进度、提交计算申请 |
| 报告交付 | `report` | 大模型 → 规则 | 2 | 交付目录与报告在哪、有什么；申请重出后处理与交付 |
| 数据质检 | `qa` | 大模型 → 规则 | 2 | 客户数据与环境齐不齐（换台机器能否复现）、每个态的结果质检（连续性 / 对账 / 副作用） |

- 声明在 `swbrain/agents/registry.py`，分派在 `swbrain/agents/orchestrator.py`，一二维那三个智能体的动作实现在 `swbrain/ontology/actions/hydro.py`。
- **降级是逐层的**：Harness 起不来退直连大模型，大模型不可达退规则规划器，每一步都在回答的 `note` 与轨迹里注明。
- 管理端（`/admin.html`）能改：启用/停用某个智能体、停用它名下某些动作、改分派关键词；改动存 `out/agents/overrides.json`，删掉即回缺省。

## 4. 分派规则（`orchestrator.py`）

- 每个专业智能体一组**领域词**：至少命中一个才会分给它；名下动作的意图词只加分（避免「检查井」「调度结果」这类说法被抢走）。
- 一句话同时命中两个智能体的**核心**领域词（例：「算完了吗？质检过了没有？」），两个都分，最多两个。
- 情景名（模型版 / M61 / R61 …）只算上下文，单靠它不构成去处。
- 都没命中，交给调度研判兜底。每次分派的理由写进轨迹。
- 有大模型时先让大模型调 `delegate(agents, reason)` 分派，出错退回上面的规则。

## 5. 两条入口，差别要说清

| | 控制台对话抽屉 | Harness 原生 Web UI |
|---|---|---|
| 入口 | 顶栏「智能体」 | 控制台抽屉里「在 Harness 打开」（由服务托管启动） |
| 局域网 | 直接用（`http://10.0.0.47:8766/`） | **只给管理员**：经控制台服务里的反向代理 `10.0.0.47:3081` → `127.0.0.1:3080`（见 5.1） |
| 分派 | 主智能体自动分派给四个专业智能体 | **不自动分派**：预设下拉里自己选（四个预设与四个工作智能体一一对应） |
| 身份 | 平台主体号（统一身份）：动作日志记 `sdip:<主体号>` | 只读共享凭据：记 `sdip:harness-web` |
| 能做什么 | 读 + 写（按职能：FIELD / ALERT / PLAN / ADMIN 判，写动作另有闸） | **只读**：写动作在 MCP 桥就被拒并提示到控制台 |
| 子智能体 | sdk profile 默认开着（可派 `subagent`） | 已打开 `subagent` / `subagent_fork` / `list-agents` |
| workflow 编排 | sdk profile 默认开着 | 已打开（2026-10-02） |
| 会话上限 | 按页面会话 id 保留上下文 | 一个浏览器只开一个标签页（Harness 自身连接上限） |

为什么 Harness 那条入口只读：dsh 的 MCP 客户端 `headers` 是**静态配置**（`z.dict(String)`），按会话传不了身份；
那边又只有一个共享的一次性 token，分不出是谁在用。所以宁可不给它写能力，也不让「不知道是谁」的人写数据。

### 5.1 Harness 原生 Web UI 的局域网入口（2026-10-02）

dsh 只肯听 `127.0.0.1`：`--host 0.0.0.0` 它直接拒绝启动（「would expose remote code execution to the network」）。
所以 dsh 不对外，局域网走控制台服务里的小反向代理 `swbrain/dsh_lanproxy.py`：

```
局域网浏览器 ──► 10.0.0.47:3081（代理，[agent.dsh].lan_port）──► 127.0.0.1:3080（dsh，web_port）
```

| 代理做的事 | 为什么 |
|---|---|
| 只放管理员（统一身份 `SWBRAIN.ADMIN`；共享口令看管理员 cookie） | Harness 能在服务器上执行代码；工具层只读，但 shell 不归我们管 |
| 带 Origin 的请求，Origin 必须是代理自己 | 防跨站 |
| 把 Host / Origin / Referer 改成 `127.0.0.1:3080` | dsh 的 `/api` 与 WebSocket 只认回环主机 |
| 去掉控制台自己的 `swb_*` cookie；回来的 Location 改回代理地址 | 不把控制台会话交给 dsh；跳转不落到访问者自己电脑上 |
| WebSocket（`/api/remote.mux`）升级后双向原样转发；建立会话记管理审计 `harness_lan_open` | 页面靠它通信；留痕 |

- 控制台的会话 cookie 按主机不按端口：在 8766 登录过，到 3081 浏览器会带上，所以不用再登录一次。
- dsh 自己的一次性 token 照样要：局域网管理员在控制台点「在 Harness 打开」拿到 `http://10.0.0.47:3081/?token=…`；非管理员点会被告知用控制台对话。
- `lan_port = 0` 关掉局域网入口。实测（2026-10-02）：经代理 token 换 cookie（303）、带 cookie 取页面（200）、WebSocket 升级（101）都通；不带 cookie dsh 仍回 401。

## 6. 子智能体：能派，但身份分不出来

- dsh 自带一整套子智能体机制（`dsh-subagent` / `dsh-tool-subagent` / `spawn-in-process` / `fork-in-process` / `client-ui-subagent`）。
- 控制台走的 sdk profile **默认开着**；原生 Web UI 那份默认关着，2026-10-02 已打开（`agent/dsh/web.patch.yml`）。
- 实测：让主智能体派一个子智能体去查积水点数，14 s 返回，子智能体确实调到了 `mcp__swbrain__count_points`，数字与主智能体自己查的一致。
- **限制**：子智能体的工具调用与主智能体在动作日志里记**同一个身份**。原因在 dsh 这边——MCP 客户端调工具只发 `{name, arguments}`，没有元数据通道；dsh 又明确禁止插件改写参数（`PreToolDecision` 注释：「Input rewriting is excluded because arguments are already logged and presented」）。
- 要做到「审计追到子会话」，唯一做法是给 dsh 写一个插件挂在 `tools/execute` 上，由插件带着子会话号来请求我们的服务（子智能体确实有自己的子会话：`exec.agent.sessionId`、`parentSession`）。代价是仓库里多维护一个 node 插件包，而 dsh 还是 developer preview、内部接口会变。**有审计要求时再做。**

### 6.1 workflow：一次派多个子智能体

dsh 自带的编排能力，建在子智能体之上：

| 组件 | 作用 |
|---|---|
| `dsh-tool-workflow` | 给模型的工具：模型**现场写**一段 JS 编排脚本 |
| `dsh-workflow-worker-thread` | 在独立线程里执行脚本；脚本里的 `agent()` 落到 `ctx.subagents`，派出子智能体 |
| `ui-workflow-run` | Harness 页面上显示运行过程（分几个阶段、每个子智能体在干什么） |

- 用法：在控制台对话或 Harness 页面里说「用 workflow……」，描述要并行或分步做的几件事。适合「同时查几个情景对比」「先查 A、再按结果查 B」。
- 实测（2026-10-02，控制台）：「用 workflow 并行派两个子智能体，一个查客户清单有多少积水点，一个查 50 年一遇有多少」→ 模型自己写了脚本 `flood-point-count-parallel`，2 个子智能体并行，返回客户清单 845、50 年一遇 448，两个口径分开写清楚，55 s。
- 限制：
  - 脚本是模型**每次现写**的，不是存下来的固定流程。要「每天固定跑 A → B → C」得另做（存脚本模板，或做成服务里的定时任务）。
  - 子智能体的身份分不出来（见上）。
  - Harness 页面那条入口只读，workflow 里的写动作同样被拒。
- 配置：sdk profile 默认开着；web 的默认组合关着，`agent/dsh/web.patch.yml` 打开了 `tool-workflow` 与 `workflow-worker-thread`。改过补丁要**重启** Harness Web UI 才生效（开着的进程加载的是启动那一刻的配置）。

## 7. 两步加东西

**加一个动作**（智能体获得一项新能力）：

1. `schema.py` 的 `ACTIONS` 里加一条 `ActionType`（参数、前置条件、副作用、`intents`、示例、`owner`）；
2. `runtime.py` 加 `_act_<api>(P)` 与 `_sum_<api>(res, P, lang)`；
3. 跑 `python -m swbrain.ontology --check` 与 `tests/test_ontology.py`——大模型的工具声明、控制台示例、文档表格都会自动跟上。

**加一个智能体**（换一组职责，2026-10-02 起管理端可直接建）：

1. 管理端 → 智能体 →「＋ 新建智能体」：填 id、名称、职责、分派关键词，从现有动作里勾一组（按归属分组列出，会写数据的标出）；
2. 创建后即时生效：主智能体按它的关键词分派给它；Harness 那边自动生成一份预设（`.agent-presets/<id>/`），**已经开着的 Harness 页面要重新打开**才看得到。

能做与不能做：

| | |
|---|---|
| 能 | 起名字、写职责、选一组**现有**动作（可以和内置智能体重叠）、给分派关键词；之后像内置的一样启用 / 停用 / 停用其中某个动作；删除 |
| 不能 | 造出新的动作能力——那要写代码（上面「加一个动作」三步） |
| 不能 | 删内置的五个智能体（只能停用） |

存放与判定：

- 存 `out/agents/custom.json`，和 `overrides.json` **分开**：「恢复缺省」只清覆盖，不会把用户建的智能体删掉。
- 权限两层：动作的原主人停用了它，自建智能体也调不了；另外只能调它自己勾的那几个（`Runtime.act` 按调用方标签 `agent:<id>` / `dsh:<id>` 判）。
- 统一身份下照旧按**发起人**的职能判：自建智能体勾了 `issue_alert`，没有 `SWBRAIN.ALERT` 的人照样签不了。
- Harness 预设里写死了它勾的动作清单（`SWBRAIN_ACTIONS`），MCP 桥只暴露这几个——容器里读不到 `out/` 也一样。
- 没有大模型时的兜底：在它勾的动作里按意图词打分取一个；必填参数从话里凑不齐就不调（不瞎猜）。
- 新建 / 删除要 `SWBRAIN.ADMIN`，记管理审计（`agent_create` / `agent_delete`）。

## 8. 长时计算：申请 → 批准 → 执行（`swbrain/agents/computejobs.py`）

一次一二维计算要跑几小时到一天、占满 CPU，所以智能体**只能申请**，起计算要管理员批准。

```
智能体 hydro_submit / report_submit ──► pending（out/agents/jobs/<id>.json）
管理端「批准」──► approved ──► 独立执行进程（python -m swbrain.agents.computejobs _exec <id>）
                              └─► 等机器空 ──► tools/c1_pipeline.py（docker 容器 c1pipe_<情景>_<态>）
                              └─► 写回 done / failed（+ 退出码；快速验证附判定摘要）──► 接着起下一条 approved
```

| 环节 | 做法 |
|---|---|
| 类型 | `compute`（建模 → 计算，可接着设计并算 v3）、`post`（后处理与交付）、`prep`（准备中间数据）、`selftest`（快速验证：合成算例约 2 分钟、14 项判定，不用填情景） |
| 去重 | 同样步骤、还没结束的申请不再重复提交 |
| 批准 | **只看角色**：有管理权限就能批，含自己提交的（2026-10-02 用户定）；提交人（`requested_by`）与每次状态变化（`history`）都记主体号，另有管理审计 |
| 同时只跑一条 | 队列里有在跑 / 暂停的，新批准的排队，前一条结束时自动接上 |
| 队列外的计算 | 命令行后台链起的一二维容器正在算时，执行进程先等（每 60 s 看一次 `docker ps`），机器空了再开算；任务的 `note` 写明在等谁。暂停着的不挡；快速验证不等；docker 查不到也不挡 |
| 不被服务重启打断 | 执行进程是脱离的（Windows `DETACHED_PROCESS`），重启控制台不影响 |
| 进度 | 不推送：查询时读各态模型日志尾部（算到几小时、百分比、淹没面积、最深、剩余墙钟粗估——按平均速度外推，雨峰后偏乐观）；`docker ps` 里的一二维容器也列出来（只读） |
| 掉线 | 标着 running 但执行进程不在、也没写回结果 → 下次查询时标 failed 并注明原因 |
| 暂停 / 恢复 / 取消 | `docker pause` / `unpause`（进度在内存里，适合临时让路）；取消 = 停容器 + 结束执行进程树 |

已知限制（2026-10-02）：

- 不能断点续算：机器或 docker 重启，算到一半的就没了，只能从头算（D24 L2+suggested 就是这样丢的：9-30 21:52 docker 中断，`--rm` 容器被删；那次的范围也不对，2026-10-02 已整场作废）。
- 快速验证不在 `c1pipe_*` 容器里跑，「暂停」对它只改状态。
- 任务文件没有加锁：两个管理员同一瞬间批准，理论上可能同时起两条。
