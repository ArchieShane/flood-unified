# 预测侧 ↔ 优化侧 接口约定（v1，2026-09-15）

分工：**预测**归另一个项目（一维二维水动力模型 + 城市内涝世界模型），**优化**归本系统（swbrain）。两边只交换三种 JSON 文件，对象用源库编号相认。代码里的定义在 `swbrain/contracts.py`，样例在 `exchange/examples/`。

```
预测侧                                 优化侧（本系统）
─────                                  ──────────────
基线预测  ──prediction_state──▶  exchange/predictions/    并入状态表，用模型量重排严重度
                                        │
                                        ▼  生成干预集合、代理评估、预算内组合
          ◀──whatif_request───   exchange/requests/       每条入选建议一个集合 + 一个打包集合
评估每个集合 × 情景
          ──whatif_result────▶   exchange/results/        覆盖代理评估，重排、重发
```

## 1. 对象编号

| 对象 | 键 | 来源 |
|---|---|---|
| 管段 | `gid`（首选）、`unitid` | pipe.dmt_irrigationstormwater_abudhabi_network.sw_edge |
| 节点 | `vertex_id` | 同库 sw_edge_vertices_pgr.id；进水口等资产另带 `unitid` |
| 出水口 | `unitid` | pipe.dmt_irrigationstormwater_abudhabi.outfall |
| 网络版本 | `network_version` 字串，如 `pipe@2026-09-15` | 两边各自记录，不一致时优化侧报警不合并 |

标高统一用**相对 MSL 的米**（源库的 level 字段减 100）。坐标 WGS84 经纬度。 该基准 2026-09-19 用客户 5 m DTM 校核：6,000 个进水口井盖标高 − DTM 中位 99.8–100.2 m，82% 在 ±0.5 m 内。

## 2. prediction_state（预测侧 → 优化侧）

一个文件 = 一个情景 × 一个干预集合（基线时 `intervention_set_id` 为 null）下的模型结果。

```json
{
  "schema": "swbrain.prediction_state/1",
  "run_id": "hydro-2026-09-20-001",
  "model": {"name": "AD 1D2D", "type": "1D2D | world", "version": "0.9"},
  "network_version": "pipe@2026-09-15",
  "scenario": {"name": "强降雨", "rain_mmh": 60, "duration_min": 60, "return_period_yr": 10, "tide_m": 1.0, "event_id": null},
  "intervention_set_id": null,
  "nodes":    [{"vertex_id": 157832, "unitid": "SW_MBZ_Z17_01_INL_18922", "max_depth_m": 0.32, "flood_volume_m3": 410, "flood_duration_min": 55, "max_hgl_m": 3.9}],
  "edges":    [{"gid": 48630, "max_flow_m3s": 0.61, "max_fill_ratio": 1.0, "surcharge_min": 40}],
  "outfalls": [{"unitid": "SW_MUS_MN3_OFL_83", "tide_locked_min": 95, "max_discharge_m3s": 0.8}],
  "cells_geojson": "predictions/hydro-2026-09-20-001_depth.geojson",
  "kpis": {"flood_volume_m3": 182000, "flooded_area_m2": 1200000, "affected_inlets": 2140, "affected_buildings": 380, "surcharge_len_km": 610, "tide_locked_min": 95}
}
```

- `nodes / edges / outfalls` 三段能给几段给几段；只给 `kpis` 也能用，只是建议不能按位置重排。
- 世界模型给的是 2D 网格结果时，把网格深度写成 GeoJSON 放 `cells_geojson`，`nodes` 可以留空。
- 优化侧只读最新的基线（同情景取文件时间最新）。

## 3. whatif_request（优化侧 → 预测侧）

```json
{
  "schema": "swbrain.whatif_request/1",
  "request_id": "wr-3f9a...", "created_at": "2026-09-15T20:30:00+04:00",
  "network_version": "pipe@2026-09-15",
  "baseline_prediction_run": "hydro-2026-09-20-001",
  "scenarios": [{"name": "常规", "rain_mmh": 30, "duration_min": 15, "tide_m": 1.0}, {"name": "强降雨", "rain_mmh": 60, ...}],
  "kpis_wanted": ["flood_volume_m3", "affected_inlets", "surcharge_len_km", "tide_locked_min", "..."],
  "reply_to": "D:/阿布扎比/排水智能体/exchange/results",
  "intervention_sets": [
    {"set_id": "p42", "label": "Al Danah：管段 ... 由 DN1200 扩至 DN2600", "cost_aed": 1560000, "proposals": [42],
     "interventions": [{"type": "pipe_upsize", "target": {"gid": 108245}, "params": {"diameter_mm": 2600}, "proposal_pid": 42}]},
    {"set_id": "bundle-top10", "label": "入选前 10 条打包", "interventions": ["...上面各集合的干预合在一起..."]}
  ]
}
```

干预类型（`type`）与参数，预测侧按此改模型输入：

| type | target | params | 含义 |
|---|---|---|---|
| pipe_upsize | gid / unitid | diameter_mm | 换管径，标高走向不变 |
| add_storage | vertex_id, lon, lat | volume_m3, invert_m, outlet_type=infiltration/orifice/pump | 节点旁加塘/池/渗井群 |
| add_pump | outfall_unitid / vertex_id | capacity_m3s, on_level_m, off_level_m | 出水口前加泵或增容 |
| tide_gate | outfall_unitid | mode=flap/controlled | 拍门改可控闸 |
| connect | from_vertex_id, to_vertex_id | diameter_mm, length_m, invert_up_m, invert_dn_m | 新增管段把无出路支接通；to 为 null 时由预测侧取最近有出路节点 |
| fix_topology | gid | action=reverse/remove/relink | 数据修正，预测侧照改后重算基线 |
| add_inlet | lon, lat, to_vertex_id | count | 补进水口 |
| temp_pump | vertex_id | capacity_m3s, hours_before_event | 事件前临时移动泵（调度） |
| pre_drain | unitid | target_level_m, hours_before_event | 事件前预排塘/池（调度） |

请求同时落在 `exchange/requests/<request_id>.json`；`[exchange].http_url` 非空时再 POST 一份同样的 JSON。

## 4. whatif_result（预测侧 → 优化侧）

```json
{
  "schema": "swbrain.whatif_result/1",
  "request_id": "wr-3f9a...",
  "model": {"name": "AD 1D2D", "version": "0.9"},
  "results": [
    {"set_id": "p42", "scenario": "常规",
     "kpis": {"flood_volume_m3": 150000, "affected_inlets": 1700},
     "kpi_delta_vs_baseline": {"flood_volume_m3": -32000, "affected_inlets": -440},
     "prediction_run": "hydro-whatif-p42-常规"}
  ]
}
```

- 放到 `exchange/results/` 下即可，文件名随意；一个文件可含多个请求的结果，靠 `request_id` 与 `set_id` 对上。
- 优化侧把有结果的集合从「代理评估」切换成「外部评估」，收益分按 `[whatif.kpi_weights]` 把 `kpi_delta_vs_baseline` 折算，重新做预算内组合与排期。
- 没结果的集合保留代理评估分，标 `eval_source = surrogate`。

## 5. 优化侧对外承诺

1. 不改源库、不改预测侧的任何文件，只读 `predictions/` 与 `results/`，只写 `requests/`。
2. 每次运行是新的 `run_id`；建议、方案、排期都进 `sw_brain.swbrain.*`，历史不覆盖。
3. 收益分的权重、成本单价、预算全在 `config.toml`，改了重跑即可，不改代码。
4. 干预集合的 `proposals` 字段回指建议编号，预测侧的每个结果都能追到是哪条建议、哪段管、哪个节点。


## 6. flood_points（世界模型 / 水动力模型 → 优化侧）

一个文件 = 一个情景下的城市积水区分布，放 `exchange/predictions/`，文件名含 `flood_points`。样例 `exchange/examples/flood_points.example.json`。

```json
{
  "schema": "swbrain.flood_points/1",
  "run_id": "gwm-2026-10-01-050yr",
  "model": {"name": "GWM", "type": "world", "version": "0.3"},
  "network_version": "pipe@2026-09-15",
  "scenario": {"name": "50年一遇", "return_period_yr": 50, "rain_depth_mm": 120, "duration_min": 360, "tide_m": 1.1, "start": "2026-10-01T02:00:00+04:00"},
  "points": [{
    "fp_id": "FP-0001", "geometry": {"type": "Polygon", "coordinates": [[...]]}, "lon": 54.5015, "lat": 24.411,
    "area_m2": 42000, "max_depth_m": 0.55, "volume_m3": 9800, "duration_min": 420, "land_use": "road|tunnel|access_road|plot",
    "hydrograph": [{"t_min": 0, "depth_m": 0.0, "volume_m3": 0, "inflow_m3h": 0}, {"t_min": 180, "depth_m": 0.55, "volume_m3": 9800, "inflow_m3h": 2600}, "..."]
  }],
  "road_impacts": [{"edge_id": 123456, "max_depth_m": 0.5, "t_from_min": 120, "t_to_min": 400}]
}
```

- `hydrograph` 是调度的关键：没有它系统只能按三角形近似算某时刻的体积与入流。`t_min` 为距事件开始的分钟。
- 世界模型输出是栅格时，请按连通积水面聚合成 `points`，一个面一条；深度取面内最大，体积取面内积分。
- `road_impacts` 可选；缺省时系统用积水面与路段中点的空间关系判断路段通行。
- 可选英文字段：`scenario.name_en`、`points[].note_en`。缺省时优化侧按模板翻译（“50年一遇（模拟）”→“50-year (simulated)”），认不出的原样显示。

### 6a. 世界模型（Abu Dhabi Urban Flood GWM API）→ flood_points 的适配器

世界模型以 Docker 容器 `abu-dhabi-gwm` 部署在本机（`http://127.0.0.1:8090`，Bearer token 在 `D:/AbuDhabiGWM/api-token.txt`），
输出是 250 m 格网（EPSG:32640，147×188，16,761 陆地格）、每 5 分钟一帧的地表水深，落在 `D:/AbuDhabiGWM/runs/<run_id>/`：

| 文件 / 接口 | 内容 |
|---|---|
| `run.json` | 请求（总雨量、历时）、情景（基线事件 noaa-isd-ae-202404151200-0327、雨量倍数、时间尺度）、指标（最大水深、受影响格、地表蓄水代理）、时间轴（385 帧×5 min） |
| `surface_depth_labels_250m.npz` | `depth_m[t, cell]` float32、`time_seconds[t]`、`x[189]`/`y[148]` 格边、`land_mask[147,188]` |
| `GET /v1/runs/{id}/map` | 最大水深与首帧的 GeoJSON（每格一个 250 m 方块，属性 depth_m / maximum_depth_m / cell_id） |
| `GET /v1/runs/{id}/timeseries?timeIndex=k` | 第 k 帧 GeoJSON |

适配器 `swbrain/gwm.py`（`python -m swbrain.gwm --mm 100 --hours 24` 或 `--return-period 50` 或 `--run-id ...`）把格网聚合成积水点：
≥ `depth_min_m` 的格算积水，3×3 局部极大值做核、核间距 ≥ `separation_m`，每格归到 `assign_radius_m` 内最近的核，每核出一个点
（几何 = 归属格并集，体积 = Σ 水深×格面积，过程线按 `hydrograph_step_min` 重采样），写到 `exchange/predictions/flood_points.gwm-<run_id>.json`。
附加字段：`scenario.suggested_decision_time_min`（积水格数达末时刻一半的时刻，调度缺省决策时刻）、`aggregation`（统计）、`points[].gwm`（核格、格数、起涝时刻）、`model.known_behaviour`。

**重现期开关**：页面顶栏选 10 / 25 / 50 / 100 年，打 `/api/return_period?yr=`，服务端按 `config.toml` 的 `[idf.return_periods]` 把重现期同时换成 15 分钟峰值雨强（喂管网承载筛查）与 24 小时总雨量（喂世界模型推演，幂等键 `swbrain-rp<yr>-<mm>mm-<h>h`），再重建调度上下文；首次约 30 s，之后按重现期缓存。IDF 表现为占位估计，拿到 ADM/NCM 曲线后只改配置。原来的雨强滑杆降为总览页里的专家控件，只影响管网筛查。

世界模型的两条已知性质，调度结论要连带说明：**水深只涨不退**（无退水项，32 小时末仍是峰值），**100 mm/24 h 时约 68% 的降雨在末时刻仍留在地表**。模型卡自述为研究级仿真器，不替代物理求解器。

## 8. dispatch_plan（优化侧 → 现场）

`out/dispatch/dispatch_plan.csv` 与接口 `/api/dispatch?t=<分钟>`：每行一台泵一次任务：wave、unit_id、model、from、fp_id、depart_min、travel_min、arrive_min、pumping_from_min、site_rate_m3h、drain_min、done_min、within_target、discharge_to。预置方案在 `out/dispatch/preposition.json`，按预警等级给驻地、覆盖的积水点、建议泵数。

## 9. hotspots（客户热点清单 → 优化侧）

来源：DMT 各市政区的 Stormwater Hotspot Analysis 工作簿（ADM 全量 507、AAM 184、DRM 155；2026-09-09 v4.x）。`python -m swbrain.hotspots --dir <目录>` 解析成 `exchange/hotspots/hotspots.json`，样例 `exchange/examples/hotspots.example.json`。

| 字段组 | 字段 | 用途 |
|---|---|---|
| 身份 | hotspot_id（区-序号）、region、area、location、lon/lat | 地图图层「客户热点」 |
| 判断 | criticality（Very High/High/Medium/Low）、network_available、root_cause（capacity/no_network/topography/other）、root_cause_raw/details | 积水点 300 m 内有热点 → 优先级按重要度加权（[hotspots.criticality_weight]） |
| 预案 A（设计标准内） | planA_manpower / pumps / pump12 / pump8 / pump6 / tankers / budget_aed | 没有泵队台账时按片区总量生成 `exchange/fleet.plan_a.json`（驻地取片区重心最近民防站，排量按尺寸估） |
| 预案 B（超标） | planB_manpower / pumps / tankers / budget_aed | 预留 |
| IDD 干预 | idd_planned_flag、idd_category、idd_type、idd_stage、idd_owner、idd_idas_approved、idd_mobilization、idd_completion、design_event_current/future | 建议卡「客户热点」行：已有 IDD 项目的建议要与之对表 |

对照统计进 `summary.json["客户热点"]` 与 `/api/dispatch` 的 `hotspot_stats`：按区/重要度/根因/IDD、预案 A 总量、ADM 热点与本系统汇水区终点的邻近、世界模型在热点格上的命中率（≥0.15 / ≥0.3 m）。客户热点是现场经验的地面真值，命中率是预测侧的验收指标之一。

## 10. 地形字段（5 m DTM，可选）

配置 `[terrain].dtm_path` 指向客户 DTM 时，run 会：(1) 用 DTM + 100 补井盖标高缺失/为 0 的进水口，无管底标高的管段在地面坡度 ≥ 默认坡度时改用地面坡度（`slope_flag = DTM地面坡度`）；
(2) 对每个客户热点做「灌到溢出」填洼分析，结果写 `out/state/hotspot_terrain.parquet`，并带进 `console/data/hotspots.geojson` 与 v3 工作簿 Hotspots 表最右 5 列。

| 字段 | 含义 |
|---|---|
| `dtm_z` | 热点坐标处 DTM 海拔（m，NADD≈MSL） |
| `low_z` | 热点 30 m 内最低格海拔（种子） |
| `spill_z` | 洼地溢出水位：水面到这个高程就漫向邻区 |
| `depth_max_m` | 溢出水位 − 最低点 = 洼地最大可积水深 |
| `pond_volume_m3` | 灌到溢出的体积（5 m 格累加） |
| `pond_area_m2` | 溢出水位下的积水面积 |
| `terrain_note_zh` / `terrain_note_en` | 空 = 正常；「无明显洼地」<5 cm；「洼地延伸出分析窗」体积为下限；「紧邻海/水体」可自流；「大范围洼地」>25 ha 体积是区域性的 |

DTM 是客户数据，不进仓库；没有文件时上述字段不出现，其余功能不变。

### 10a. 子汇水区（`swbrain/catchments.py`）

配置 `[terrain.catchment]`。每个进水口/雨水井顶点得到 `area_m2`（DTM 子汇水区，同格均分、上限 20 ha）与 `c`（地表覆盖加权径流系数），缓存 `out/state/inlet_catchments.parquet`；
沿管网累加后每段管带 `area_basis = dtm` 与 `runoff_c`，能力比、法定标准达标、当场算、汇水区径流量、热点工作簿的 C 都改用它们。上游没有进水口的段退回道路法（`area_basis = road`）。

### 6b. 本系统积水点（`swbrain/floodpoints.py`，`model.type = "system"`）

`[dispatch].flood_source = "system"` 时，第三道防线的积水点不再取世界模型，而是由本系统按重现期当场生成：点 = 客户热点；有管网匹配的按手册 3.6 梯形过程线算调蓄缺口（×1.05 减塘容），雨停后按 Qcap 退水；
无管网匹配的用 DTM 填洼体积做上限代理；深度与面积按 DTM 洼地缩放；`target_drain_min` 按客户预案 A 分级目标（极高 120 / 高 240 / 中 600 / 低 600 分钟）。
额外字段：`source`（network_gap / dtm_proxy）、`client_hotspot_id`、`client_criticality`、`spill_m3`、`note_en`；顶层 `stats`。文件写到 `exchange/predictions/flood_points.system-{rp}yr.json`，不进仓库。
`flood_source = "prediction"` 恢复用世界模型输出。

### 6c. 退水重演（`swbrain/replay.py`，`GET /api/replay`）

`/api/replay?fp=ADM-189[&t=210][&pumps=8in:2@250,6in:1@300]`：对一个积水点按 5 分钟步长重算水量平衡。自然去水从基线过程线反推（n = max(入流 − dV/dt, 0)），
所以本系统的点雨停后按管网能力退水，世界模型只涨不退的点只有泵能排。不给 `pumps` 时用当前决策时刻调度单里派到该点的泵（到位 = 到达 + 架设）；
给 `pumps` 时按「型号:台数@到位分钟」手动派泵。返回两条曲线（`base_m3` / `pump_m3`，另有按 √(V/V峰) 缩放的水深）与 KPI：退干时刻、峰值、积水时长（>50 m³ 的小时数）、抽走水量、提前分钟。
调度结果里每个处置点带 `replay_*` 字段，顶层 `replay_summary` 给「处置点」与「全部点」两个口径的积水时长前后对比。

### 6d. 预置的价值（`dispatch.preposition_value`）

`/api/dispatch` 返回的 `preposition[等级]` 多一个 `value`：`depart_min`、`units_placed`、`sites`、`points_with_pumps`、`arrive_median_min` / `after_arrive_median_min`、
`flood_h {base, after, pre}`、`vol_hours {…}`、`saved_vs_base_pct` / `after_saved_vs_base_pct` / `saved_vs_after_pct`、`within_target {pre, pre_n, after, after_n}`、`level_iii_served {pre, after}`、`t_empty_median_min {pre, after}`、`plan`（预置调度单）。
配置 `[dispatch].preposition_depart_min`（默认 30）。

## 11. 情景目录（`swbrain/scenarios.py`）

页面重现期开关的每一档是一个情景 key，同时驱动管网筛查（15 分钟雨强，事件情景按片区不同）、积水点（各历时雨强）与第二、三道防线：

| 类型 | key | 雨强 | 来源 |
|---|---|---|---|

## 16. 全网溢流量（`swbrain/networkflood.py`）

- `/api/return_period` 的 `scenario.network_flood` 与 `/api/scenario?i_mmh=` 的 `network_flood`：`total_m3`、`edges` / `edges_spilling`、`spilling_len_km` / `spilling_len_share`、`peak_spill_total_m3s`、`d_star_median_min`、`top_edges[]`（gid / V_m3 / zone / spill_m3s）、`by_zone[]`（zone_name / V_m3 / len_km / n_spill）、`method`。目录里的情景按 key 缓存；专家滑杆的任意雨强按 10 年 IDF 等比缩放。
- 算法：推理公式 q = K·C·i(d)·A_local 给每个节点，沿 DAG 按拓扑层向量化下推，节点流量按出边数均分，每段 spill = max(Q − Q_full, 0)、pass = Q − spill；对 d ≥ tc 的每个 IDF 历时算手册 3.6 梯形体积取最大；<50 m³ 不计。不含下游顶托与塘泵闸调蓄。DAG 分层缓存在 out/state/netflood_prep.npz。
- 事件雨型：`floodpoints.load_hyetographs` 读 `[scenarios].hyetographs_file`（缺省 out/dmt_model/rain_events.json，`python -m swbrain.dmtmodel` 生成：{情景 key: {区域: {dt_min, cum_mm, depth_mm, i15_mmh, model, gauge}}}）。事件情景的管网缺口点用 `hydrograph_from_hyetograph`（逐 5 分钟：入流 = K·C·A·过去 tc 内平均雨强，出流 ≤ Q_cap，雨停后退到 0 或 48 h），过程线 15 分钟一点；没有雨量计的区域借 24 h 雨量最大的那条按 `p24_by_area` 缩放。flood_points 的 `stats.hydrograph_basis` 标 `observed_hyetograph` 或 `manual_3.6_trapezoid`。
- 顶托代理：`network_flood.backwater`（edges / len_km / len_share / max_m / ratio_thr，config `[networkflood]`）——自己不溢、沿流向 ≤ backwater_m 内有溢流段、峰值利用率 ≥ backwater_ratio 的管段。run.py 把 10 年一遇的 `nf_spill_m3_10` / `nf_backwater_10` 写进 es.parquet，并按匹配管段挂到热点（hotspots.geojson 属性 `edge_gid` / `nf_spill_m3_10` / `nf_backwater_10`，`hotspot_stats.nf_10`，out/state/hotspots_enriched.parquet）；dmtmodel.compare 的 `hotspot_vs_overflow.concordance` 给「本系统标记 vs DMT 溢流人孔」的一致性四格。
- `python -m swbrain.dmtmodel` 的 compare.json 多了 `our_flood_inside_m3{key}`（模型边界内本系统溢流量）与 `parsons_flood_m3`（config `[dmt_model.models.X].parsons_flood_m3`），并写 console/data/dmt_compare.json 给「数据与可信度」页的「DMT 模型对表」表。

## 24. 退水方案：什么时候退水、怎样最快（`swbrain/recession.py`，`/api/recession`）

- `GET /api/recession?fp=ADM-62&rp=50[&t=240][&upsize=0]`：围绕一个积水点的两个终极问题。`options[]` 依次是：`natural` 不派（自然退水）、`global` 全局最优调度给它的（第三道调度单，含罐车）、`single` 单点最优（现有泵队里最多 max_units_per_point 台只给它，枚举「最晚到位是第 k 台、前 k 台里排量最大的 n 台」取排干最早）、`prepo` 预置最优（同一批泵提前放在最近候选驻地，preposition_depart_min 出发）、`tankers`（无排放去处的点）、`upsize_<DN>` 换管（工程，来自单热点详情曲线）。每项给 `t_empty_min`（事件开始后分钟，None = 48 h 内不退）、`flood_h`、`within_target`（≤ 决策时刻 + 目标时限 + 60 min）。
- `single_vs_global`：单点最优比全局给的快多少（`delta_min`）、会抢走全局调度里的哪些泵（`units_taken_from_global`）、这些泵原本服务的点与它们退干合计推迟多少（`displaced_points[].saved_min_lost`，来自第三道每点重演的 replay_saved_min）。`need_units_for_target`：只顾它要几台才能在目标时限内排干（最多枚举 8 台），做不到给原因。`wait_until_min`：入流大于可派排量时建议等到的时刻。`recommendation.zh/en`：一段话结论，首句是最快的手段。
- 全部数字与第三道页面同一套过程线与重演器；不重算水力学。控制台单热点详情底部「什么时候退水 · 怎样最快」表即此接口；本体动作 `recession_options` 同义（问法：「ADM-62 什么时候能退水，怎样最快」）。

## 26. 对话框驱动地图与客户五问（本体动作 `count_points` `world_model_new_points` `recession_batch` `cost_summary`）

- 四个新动作对应客户连着问的五个问题：有多少积水点 → 世界模型新增了多少 → 其中最严重的 → 怎么加快这些点退水 → 成本与代价。`recession_batch` 逐点跑退水方案并汇总（最快手段分布、达标数、需泵台数、运维费用 / 全部预置 / 全部事中 / 换管造价、抢走的泵与被推迟的点）；`cost_summary` 带 `fp_ids` 给这批点的账，不带给情景全局账（第三道调度费用、各级预置费用与价值、客户预案对比）。
- 退水方案每种手段现在带 `cost_aed` / `pump_hours` / `cost_kind`：运维 = 台时 × 预案 A 单价 + 动员费（dispatch.plan_cost 同口径）；换管 = `[cost].pipe_aed_per_m_by_dn` 往上取档 × 匹配管段长度（占位单价）。`recession_options` 结果加 `costs_aed`、`lon`、`lat`。
- **ui 协议**（动作结果 `ui`，控制台 `applyAgentUi` 照做）：`rp` 切情景、`tab` 切页、`hs` 打开单热点详情、`fp` 第三道选点、`layers:[…]` 开图层、`highlight:[{id, lon, lat, kind: points|hotspots|gwm, label}]` 在地图上打脉冲标记并编号、`fit: highlight|all|none`、`clear` 清除标记、`gwm` 并排世界模型、`url` 新窗口。气泡里列出标记的点，点一下定位 / 打开详情。
- `console_link`：每个动作结果都带能复现 ui 的控制台相对地址（`/?tab=&rp=&hs=&hl=id1,id2&hlk=kind`）；MCP 工具结果里是绝对地址，供在 Harness Web UI 等别处对话时给用户点开。深链接 `?hl=ADM-1,ADM-2&hlk=points` 由控制台按 id 查坐标后高亮。

## 27. 路况（`swbrain/traffic.py`，`[traffic]`，`GET /api/traffic`）

- `provider = google | simulated | none`。google 走 Routes API `distanceMatrix/v2:computeRouteMatrix`（`X-Goog-Api-Key` 只从环境变量 `api_key_env` 读；`X-Goog-FieldMask: originIndex,destinationIndex,duration,staticDuration,distanceMeters,condition,status`；`routingPreference=TRAFFIC_AWARE` 每请求 ≤625 元素，`TRAFFIC_AWARE_OPTIMAL` ≤100 且带 `trafficModel`；`departureTime` 必须是现在或未来，过去时刻自动改成现在 + 60 s）。
- 系数层：`depot_factors(ctx)` 每个驻地按本地行程分层抽样 `sample_per_depot` 个目的地，系数 = Σduration ÷ ΣstaticDuration，夹在 `[factor_min, factor_max]`；`apply(ctx, meta)` 把驻地→点矩阵按行乘系数、点→点按均值乘，`ctx["traffic"]` 记来源。精算层：`refine_plan(plan)` 对调度单里从驻地出发的行程逐对查，返回 `worst[]`（`model_min / google_min / delta_min`）。
- 缓存 `out/traffic_cache.json`：键 = 起点、终点（4 位小数）、15 min 出发时段桶；TTL `cache_ttl_min`。服务端每刷新一次换一个 `traffic_id`，调度缓存键里带它，旧路况下的解作废。
- `GET /api/traffic?refresh=1&depart=2026-09-25T14:00&t=210&rp=10cc` → `{status, meta{provider, departure_local, factors…}, by_depot[], factor_min, factor_max, refine}`；`/api/dispatch` 的载荷多了 `traffic`。
- 时变：`factor_series()` 在基准出发时刻之后每 `window_min` 再取一次系数，共 `windows_ahead` 个窗口，写进 `meta.series = {"<t_min>": {depot_id: factor}}`；`scale_at(ctx, t_now)` 给出该时刻相对基准窗口的每驻地比值与点→点均值比值，`dispatch2.build_classes` 按它缩放行程行。`/api/traffic` 返回 `series.mean_by_t / min / max`。
- 没密钥 / 请求失败：`provider` 退成 `simulated`（阿布扎比时段曲线 × `[traffic.simulated].rain_uplift`），`meta.note` 说明原因；所有输出标 `simulated=true`。

## 28. 外部源两条路（`swbrain/feeds.py`，`[feeds.*]`，`GET /api/feeds`，`POST /api/feed/<name>`）

- 四个源：`incidents`（993 报案，`swbrain.incidents/1`）、`checkins`（承包商到场，`swbrain.checkins/1`）、`bridges`（限重 / 净高台账，`swbrain.bridges/1`）、`contractors`（服务边界，`swbrain.contractors/1`）。示例在 `exchange/examples/<name>.example.json`；真实文件放 `exchange/<name>.json`（不进仓库）。
- 拉：`[feeds.<name>].url` 非空就 `GET url`（`Authorization: Bearer <token_env 环境变量>`），`poll_s` 内缓存，失败退回文件并在返回里记 `error` / `http_failed`。推：`POST /api/feed/<name>`（要口令），正文是契约 JSON（`{schema, as_of, source, rows[]}` 或裸数组），有 `id_key`（incidents / checkins / bridges 用 `id`，contractors 用 `depot_id`）按 id 覆盖，否则按整行去重；可带 `X-Source` 头记来源。
- 校验：`feeds.validate(name, rows)` 按契约逐行检查（incidents：`fp_id` 或阿布扎比范围内的 `lon, lat`，`verified` 布尔；checkins：`depot_id`/`site_id` 与非负整数 `units`；bridges：范围内坐标与正的 `limit_t` 或 `clearance_m`；contractors：`contractor` 与 `depot_id` 或 `region`）。推：返回 `received / accepted / rejected[{row, id, why}] / added / updated`，全部不合格 → HTTP 400 且不写文件；拉与读文件：不合格行不进消费方，`invalid` 计数与 `invalid_examples` 放在返回里，`/api/feeds` 每源带 `invalid_rows`。
- 消费方：`replan` 自动并入 incidents（`replan.incidents_feed` 说明来源）；`staging_status` 用 checkins（`checkins_meta` 带 url / fetched_at）；`dispatch.build_context` 用 bridges 替换模拟条目（`ctx["bridges"].source/as_of`）；`resources.build` 用 contractors（`depots[].contractor_real`）。
- 鲁棒目标：`/api/dispatch?robust=1`、动作 `dispatch_plan(robust=true)`；`[dispatch.robust].scenarios` 权重；载荷 `v2.robust = {frame, weights, labels, by_scenario{key: {points_in_plan, within_target_worse, never_empties_worse, extra_12in_equiv_total, base{…}}}, expected, expected_base}`。

## 29. 积水点生命周期层（`swbrain/lifecycle.py`，本体 RainEvent / FloodEpisode，`[lifecycle]`）

- 两个新契约走 feeds 的拉 / 推两条路：`events`（`swbrain.events/1`：`event_id`、`date` 或 `start/end`、`p24_mm`、`p24_by_area`、`scenario_key`、`kind`）与 `episodes`（`swbrain.episodes/1`：`fp_id`、`event_id`、`flooded`、`depth_m`、`duration_min`、`units`、`first_arrival_min`、`drain_min`、`stage` + `at`、`source`、`note`；同一点同一事件的多行合并）。示例 `exchange/examples/events.example.json`、`episodes.example.json`；`POST /api/feed/events`、`/api/feed/episodes`。
- 片区级证据：事件行可带 `impacted_areas`（公开报道点名的积水地名，如 Khalifa City / Zayed City / Madinat Zayed），按 `lifecycle.AREA_KEYWORDS` 的英 / 阿关键词对上热点的 `area` / `location` → 该点在该事件的经历标 `area_reported=true`、来源加 `area_report`；它不改 `observed_flooded`、不进对账，摘要里只说「所在片区有公开报道积水」。
- 事件窗口：`date` 为 YYYY-MM-DD 时前后 `event_window_days`（3）天，YYYY-MM 时整月；现场观测（`observed_at`）与 993 报案（`at`）落在窗口内就归到该事件。
- 本体接口沿用：`GET /api/object?type=RainEvent&id=2024-04`（带 POD / FAR / verdict）、`type=FloodEpisode&id=ADM-62@2024-04`、`GET /api/objects?type=FloodEpisode&event_id=2024-04`、关系 `episodes / ep_point / ep_event / ep_state / event_episodes / event_scenario / scenario_event`；动作经 `/api/action` 或对话。
- 写入：`out/events.jsonl`（open_event）、`out/episodes.jsonl`（update_episode / close_point，`{fp_id, event_id, stage, at, depth_m, units, note, source: log}`）、`out/proposal_status.jsonl`（set_proposal_status，`{pid, status, at, note}`）；`load_proposals` 叠加后者。
- 导入器 `swbrain/episodes_import.py`（`python -m swbrain.episodes_import --incidents … --event 2024-04 --dry-run | --push`、`--callcenter …`、`--polygons <gdb|shp|geojson> --layer … --event … --date …`）：把客户的事件报告表、800555 呼叫中心 / AI 巡查表、UPPC 卫星洪涝面落成 `swbrain.episodes/1`。列名按关键词猜（`--map lat=Y,lon=X,…` 可指定），坐标优先（WGS84 或 UTM 40N 自动转，300 m 内最近热点），其次地名 / 描述与热点 location 的词重合（≥ 2 词且唯一）；每行带 `match` 依据，匹配不到的行列在 `unmatched`。卫星面：热点落在面（+30 m）内 = 该事件积水（source=satellite），面外不写「不积水」。
- 对账口径：只在「记录侧与模型侧都有结论」的经历上算；`[verification]` 的 `pass_pod_min / pass_far_max / pass_depth_rmse_m`，`[lifecycle].min_observed_for_verification`（10）以下为 insufficient；`event_review` 数连续 fail 的场次，达到 `recalibrate_after_failures` 提示重校准。

## 30. 代码结构：状态 / 接口表 / HTTP 三层（2026-09-23）

- `swbrain/state.py`：服务端状态与编排（装载 `out/state`、按情景算上下文与调度、落盘缓存、求解子进程、任务表、本体与智能体）。
- `swbrain/routes.py`：接口表。一条接口 = 一个带 `@route(path, method, desc, params, prefix)` 的函数，签名 `fn(state, qs, body, req)`，返回 `dict`（200）、`(dict, code)` 或 `Raw`（报告 HTML 这类）。参数解析统一用 `s1/f1/i1/b1`。`GET /api` 返回全部接口的清单（自描述，31 条）。
- `swbrain/serve.py`：只剩 HTTP——口令与 cookie、静态文件、分发、错误码（`ActionError` → 400，其余 → 500）与 `main()`。
- `swbrain/ontology/`：`common.py`（公共助手）、`runtime.py`（装载 / 缓存 / 对象 / 关系 / 规则 / act 分发）、`actions/{points,dispatch,lifecycle,system}.py`（35 个动作的 `_act_*` 与 `_sum_*`，由 `Runtime` 多继承）。加动作：在对应域的 mixin 里写两个方法，再在 `schema.ACTIONS` 声明。

## 30b. 契约的正式模式与状态清单（2026-09-23）

- `exchange/schemas/*.schema.json`：六个源的 JSON Schema（draft 2020-12），由 `swbrain/schemagen.py` 一处声明生成；`python -m swbrain.schemagen --check` 会拿示例文件对表，并核对 schema 与 `feeds.validate()` 判定一致（不一致退出码 1）。给 ADM 侧对接的人看的就是这几份，加 `exchange/schemas/README.md` 的对照表。
- `out/state/manifest.json`：批处理 `run.py` 结束时写——构建时间、各表行数、配置指纹、代码指纹、git 提交、源库主机 / 库名（不含口令）。服务装载时读它，放进 `GET /api/health` 的 `state_manifest` 与假设总账；配置指纹与当前配置对不上会在启动日志里警告「out/state 是用另一份配置算的」。清单自己不进缓存指纹。

## 31. 运行架构：落盘缓存、异步任务、假设总账（2026-09-23）

- **落盘缓存**（`swbrain/artifactcache.py`，`[serve].disk_cache`）：情景上下文与调度载荷按 `out/cache/<指纹>/` 存。指纹 = 代码（模型层模块源码的 sha1；改本体 / 服务 / 控制台不作废）+ 配置（去掉 `[source] [output] [serve] [agent] [feeds] [lifecycle]` 后的 JSON）+ 状态（`out/state` 各文件的名字 / 大小 / mtime，加 `exchange/fleet*.json`、热点清单、预测侧给的 flood_points；本系统自己写回的 `flood_points.system-*.json` 不算）。调度载荷的键还带路况指纹与目标 / 预算 / 鲁棒。旧指纹目录只留最近 3 个。`GET /api/health` 的 `disk_cache` 报命中 / 写入 / 体积。
- **异步任务**（`swbrain/jobs.py`，`[serve].solver_workers` / `job_threads`）：`GET /api/dispatch?async=1`（stress、focus 同）与 `POST /api/replan {"async": true}` 返回 `{job_id, status}`，`GET /api/jobs/<id>` 查 `{status: queued|running|done|error, elapsed_s, result}`，`GET /api/jobs` 列最近 50 个。同样参数的任务在跑就复用同一个 job_id。求解本身在 `ProcessPoolExecutor` 的子进程里（绕开 GIL），主进程照常响应；子进程池坏了自动重建一次再退回同进程。控制台的 `apiJob()` 带 `async=1` 发起、每 1.5 s 轮询，按钮上显示已等秒数。
- **假设总账**（`swbrain/assumptions.py`，`GET /api/assumptions?rp=`，动作 `assumptions`）：列出当前依赖的模拟 / 假设 / 占位 / 未核实 / 缺失输入，每条 `{id, area, level, what, value, source, affects, fix}`。控制台顶栏常驻「本页有 N 项假设」，点开是表。
- **配置单一来源**（`swbrain/configcheck.py`）：`python -m swbrain.configcheck` 比 `config.toml` 与 `config.example.toml` 的键集（值不比），有漂移退出码 1；`--sync` 用 config.toml 重新生成示例，密钥 / 口令 / 内网主机 / 本机路径保留占位。serve 启动时做一次，只警告不拦。
- **最小 CI**：`scripts/ci.ps1`（加 `-Integration` 跑真机集成测试）与 `.github/workflows/ci.yml`（未在仓库跑过，Actions 未开）：单元测试、控制台脚本语法、本体自检、配置漂移。依赖锁在 `requirements.lock.txt`。
- **真机集成测试**：`SWBRAIN_INTEGRATION=1 python -m pytest tests/test_integration_serve.py -q`，装载真实 `out/state` 起临时端口的服务，打 11 个轻接口 + 异步任务形状 + 401/404，约 5 分钟。
